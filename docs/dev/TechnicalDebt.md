### Functional

- Controller haptic PCM drives Xbox-style motor rumble from its per-channel RMS (large/small motor, scale 2x, below 0.01 ignored, 80 ms hold); the mapping approximates waveform energy and is not measured against console hardware
- [Cancellation coverage](ARCHITECTURE.md#thread-cancellation) checks deferred request handling and recovery, not full asynchronous support or console ABI compatibility. Cancellation during file/socket I/O, sleep interruption, cancellation versus exit/detach, condition signal conservation under cancellation, and safe rejection of non-null invalid or reclaimed thread handles remain unverified. No console title or homebrew establishes the cleanup NIDs or buffer layout. Accepted asynchronous mode currently has no diagnostic for its deferred behavior.
- `--to-intel` guest module trampolines are covered only by a synthetic relinker test; no game title has been verified with them on Linux or Windows.
- On macOS (MoltenVK on an Apple GPU), 16 AGC tests fail on hardware limits:
  - Metal has no 64-bit floats (the 7 agc_driver_f64_* tests and agc_driver_division_result_modifiers);
  - it has no 64-bit atomics (agc_driver_buffer_atomics*, agc_driver_global_atomics64, agc_driver_global_atomics_float, agc_driver_global_atomics_lanes);
  - MoltenVK offers no VK_KHR_shader_clock (agc_driver_shader_clock).
- agc_driver_sdwa_float_selectors fails on macOS: an f16 multiply that should give -0.0 gives +0.0. In isolation, Metal keeps the sign through each step of the same chain (half to float, multiply, the software float-to-half conversion). The cause, found on an M1 Pro: SPIRV-Cross's MSL backend computes a precise multiplication as `fma(l, r, 0)`, which turns a -0.0 product into +0.0. A fix is submitted as KhronosGroup/SPIRV-Cross#2704; it reaches this project when MoltenVK takes that SPIRV-Cross.
- The [SPIR-V backend](../../core/shader/recompiler/SpirvBackend) works around SPIRV-Cross, which MoltenVK uses to make Metal shaders:
  - ordered not-equal is emitted as an unordered not-equal and two NaN tests on the bits, because SPIRV-Cross writes OpFOrdNotEqual as `!=`;
  - NaN tests read the bits;
  - an image atomic comes after an image-memory barrier, because Metal shows an invocation's earlier image stores to its atomics only after a texture fence;
  - subgroup results pass through a Private variable, so that SPIRV-Cross does not move them into `?:`, `&&` or `||`, where only some lanes would run them.
- On macOS every guest image keeps its own TLS block and thread pointer ([MacOsImage.cpp](../../core/relinker/elfpatcher/src/macos/MacOsImage.cpp)). Another module can reach a module's exported TLS variable only through general-dynamic access (DTPMOD64/DTPOFF64). The image initializer fills those slots from the TLS index the defining module exports. As on Windows, initial-exec access (TPOFF64) to another module's TLS fails the relink. In the executable, TPOFF64 and DTPOFF64 against its own block are resolved when relinking (the block sits `AlignUp(p_memsz, p_align)` below the thread pointer, [WindowsRelocationBuilder.cpp](../../core/relinker/elfpatcher/src/windows/WindowsRelocationBuilder.cpp)); DTPMOD64 and imported TLS symbols there fail the relink. The Linux ELF that aps5-fex loads keeps all three as dynamic relocations. TPOFF32 is rejected on every target.
- Guest fixed addresses in host-reserved ranges on macOS arm64 are backed at `guest | 1<<40` ([GuestDisplaced.cpp](../../core/libs/prx/libc/src/GuestDisplaced.cpp), D31, D33): the dyld shared region's unused tail (end of the shared cache, ~13 GiB, to 0xFC0000000, found at startup), the commpage guard (63-64 GiB) and the GPU carveout (64-448 GiB, a permanent kernel guard in every arm64 process). Known limits:
  - a translated load/store site, once patched for a displaced address, runs a stub for every pointer it sees afterwards: in a tight loop ~3-4x the cost of an unpatched access for ordinary pointers and ~2.2-2.7x for displaced ones (D49; it was ~6.5x for both before D49's one-register stub). The stub still spills one register to the stack and branches twice. Generic guest code that touches both kinds (memcpy, Mesa's upload paths in SuperTuxKart) pays it everywhere. A cheaper stub needs a scratch register FEX guarantees dead at memory ops, or rebasing in the IR;
  - the shared region tail is found from the live layout; if a macOS update maps something new after the cache, or the alias of the lower ranges is taken, those ranges drop out (logged) and fixed guest mappings there fail as host regions, as before D33. A fixed mapping inside the shared cache itself cannot be served at its address (the cache is readable host memory, so accesses would not fault): by DECISIONS D37 it is relocated to request + 0xD000000000 and the real address is returned through the in/out argument ([DirectMemory.cpp](../../core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp) `RelocateUnservableFixed`, logged on stderr, `APS5_FIXED_RELOCATE=0` refuses instead). A title that ignores the returned address and keeps using the constant (legal on the console: MAP_FIXED guarantees the address; EA's EAStdC does this) reads dyld cache bytes silently and faults on writes. ASTRO BOT (PPSA21564, 0x300000000+0x79800000) reads it back (D37's disassembly). Only direct, flexible and reserve-virtual requests relocate; file-backed and shared-memory fixed maps there still refuse;
  - native code that touches a displaced guest address directly (not through `GuestArena::HostAddress`/`HostRange`) takes two signals per load/store (~2-4 µs; native `memset` of 1 MiB at the guest address took ~4,600x as long as at the alias), and a host system call given one fails outright (EFAULT/ENOMEM: the kernel raises no signal). Translated up front (VA3 audit, 2026-10-14; `HostRange` throws for a range across the window's edge): DirectMemory (maps, protection, mlock/munlock, VirtualQuery of unregistered memory, the no-arena fixed map/unmap), the arena, write watch; file and socket I/O (sceKernelRead/Write/Pread/Pwrite/Readv/Writev/Preadv/Pwritev incl. the shared-memory paths, AIO, APR reads, `/dev/urandom` and every `HostEntropy` caller, libkernel and libSceNet send/recv/sendto/recvfrom, sendfile headers), libc `fread`/`fwrite` and the memory/string exports (memset, bzero, memcpy, memmove, memcmp, bcmp, memchr, strlen, strcmp, strncmp, strcoll, strcpy, strncpy, wmemcpy, wmemmove), mspace calloc/realloc, SaveData blob reads/writes, AudioOut/AudioOut2 PCM reads; in the AGC driver the `GuestMemory` primitives (now also `ImportWatched`), the Metal import and page wrappers (`NewNoCopyBuffer` takes the guest address: the write watch is keyed by it, the region scan/mprotect/wrap use the alias), the CPU buffer copy, command-buffer copies (IB/CIB, rewind tail), DCC key scans, image-mirror refresh, snapshot checks and staging copies, draw and storage snapshots, index-buffer reads, tiled target detile/tile, CMASK scans, write-evidence/capture/variant validation copies (tests `guest_displaced_paths`, `guest_displaced_memory`, `agc_driver_displaced_guest_memory`). Also translated (ASTRO2, 2026-10-14): libSceAgc's shader functions (CreateShader, FuseShaderHalves, GetFusedShaderSize, the CreateInterpolantMapping family, CreatePrimState, LinkShaders, GetGsPrimPayload, GetGsOversubscription) read headers through `HostShader()` (ShaderUtils.hpp) and the driver's shader registration through `HostRange` (test `guest_displaced_shaders`, 0 faults; ASTRO BOT went from over 124k faults in 40 s to under 2,048 in 120 s); libkernel pthread mutex/cond/rwlock/sem/once slots (ASTRO's mutexes are at 0x10xxxxxxxx; `guest_displaced_memory`). Every log now shows the rate: `[displaced] N faults T s after enable` at 1024 faults and each power of two. Also translated (VA8 audit, 2026-10-14; tests `guest_displaced_status`, `guest_displaced_audio`, `guest_displaced_fiber_media`, `guest_avplayer`'s displaced phase, `guest_displaced_shaders`, `agc_commands`): libkernel equeue waits and event accessors, clock_gettime/gettimeofday, event flags; VideoOut event and status exports; Pad read/info exports; AudioOut/AudioOut2/Audio3d status, parameter and attribute arrays; UserService Get* out-parameters; NGS2 (system/rack objects in the context buffer, waveforms, VoiceControl params, render outputs, state queries) and AJM (batch buffers, bitstreams, PCM outputs, sidebands); fiber objects and their out-parameters; AvPlayer frame and audio buffers and info structs; SaveData memory/param copies; AgcDriver CPU buffer copy, copy count records, held-at-submit label reads, ShaderMemory raw word reads, the DCB multi-submit arrays and rendering-wait packet; libSceAgc SetIndexSize_0600 and marker text. Still untranslated, correct but slow through the fault path: trace/verify-only reads (Recorder hook profiling, ShaderResources `Describe`, UnitShadow verify, WaitMemory's APS5_TRACE_GPU and timeout reads, LabelHistory), Videodec2, Vdecsw, Zlib, PngDec, NGS2 custom-rack/UserFx2 params and GetInfo/QueryBufferSize outputs, SaveData search results, AvPlayer init-time struct reads, Time.cpp's gettimezone/convert/clock_getres and nanosleep arguments, socket bounce copies, the libc string functions other than those above (strchr, strstr, wide-string ones...), and guest-heap realloc/calloc (the guest heap is first-fit, never in the window). Not reachable: guest thread stacks, fibers' host stacks, module images and FEX's own memory are host-placed, never displaced. Bridge arguments are not translated, and by D35 they will not be (pointer identity would leak the alias to the guest). Host system calls are covered by the host system call shim (`core/libs/hostsys/HostSyscallShim.cpp`, CMake `APS5_HOST_SYSCALL_SHIM`, ON by default): 80 of the 422 libSystem symbols the 131 prx import are defined hidden in libc and every prx (third-party objects included) and translate displaced pointers, the classification of all 422 is `core/libs/hostsys/host_imports.tsv`, and the test `host_import_inventory` fails on any unclassified import. Known limits of the shim: ioctl requests that take a pointer without encoding its size (IOC_VOID) and fcntl commands other than the listed pointer commands pass their argument through; mach_msg out-of-line descriptors are not translated; a `%s` argument of fprintf/vfprintf is read in userspace (fault path, slow); libSystem functions are resolved by dlsym on first use (write at load), so a first call from a signal handler could deadlock; libc++'s basic_filebuf/fstream (14 prx) and std::filesystem (13 prx) call libSystem from inside libc++.dylib, beyond the shim: a large fstream read/write of a displaced buffer can still reach the kernel with the guest pointer; libSceUsbd's libusb and the HID code in libSceAgcDriver pass buffers to IOKit through plug-in vtables and IOHID calls that no import inventory sees (USB transfer buffers in displaced memory would fail); raw `svc` and aio (not imported) are not covered; setjmp/longjmp save the signal mask with a libc-internal sigprocmask on the jmp_buf (host stacks only, so unaffected today);
  - native sites are never patched (signed code), and native code has no free memory within branch range (the dyld shared cache; our prx dylibs, whose neighbourhood the arena reserves), so their stubs are far: every execution is a fault plus a SIGTRAP back, unless the code ahead overwrites a register without reading it within 6 relocatable instructions (D49 `FarReturn`, shared-cache code only; it relies on that code being immutable). ASTRO BOT's libSceAgc command-buffer writers were the main source (~37k in 0.3 s) and now use host views (`Agc::Command::Host`); the last 72 per 300 s (sceAgcDcbSetIndexSize_0600, Driver::noteHeldAtSubmit, ShaderMemory::read) are gone (VA8: 0 in 300 s). Find new ones with the `unpatched (native) faults` milestones (now from the first fault) and `APS5_DISPLACED_STACKS_NATIVE=N`. The VA8 static audit covered the libraries listed above; the rest of the prx (and anything new) is unaudited;
  - a load/store-exclusive pair in native code on a displaced address can livelock (the signal clears the exclusive monitor); translated code patches both sites after their first fault and then succeeds. Apple's libraries use LSE atomics;
  - a register-offset site checks its full address (`xN + ext(xM) << s`, VA8); before, `[small + pointer]` failed the stub's check, faulted inside the stub and built one more stub per execution, a chain that grew without bound (ASTRO BOT: ~90% of its ~123k "patched sites" in 300 s were one `ldr s18, [x17, x4, sxtx]` chain, and a core walked it at 100%). The flip path still assumes bit 40 of xN is clear (true for every pointer below 1 TiB); a pre/post-indexed or immediate access whose offset carries it out of the window is still checked on xN alone;
  - patched sites live in a 1M-entry table (live sites capped at 7/8 of it) and up to 512 one-MiB stub chunks; when either is exhausted the next new site is left unhandled (fatal, logged `site table full` / `no stub memory`). Sites and their stubs are freed when the code holding them is freed (VA8, D58: FEX's code buffers through `CodePool::Free` -> `GuestDisplacedCodeFreed`; churn test 1.48M sites through the table), so only sites in live code count. Limits: FEX invalidating single blocks (SMC, guest module unload) leaves their code, and so their sites, in the buffer until the buffer is freed; native code that is unloaded (a prx dlclose, never done today) does not report its range, and a rebuilt site at a pc whose instruction changed leaks its old stub; a free scans up to the whole table (32 MiB) under the site lock with signals blocked, a few ms per code-cache clear, during which other threads' displaced faults wait. ASTRO BOT now keeps ~4-8k live sites in 300 s (it was ~123k, mostly the register-offset chain above);
  - an unaligned LSE atomic (CAS, LDADD..., crossing 16 bytes) on a displaced address, or in a displaced-access stub, is not handled: FEX's unaligned handler is skipped for [0x180000000, 448 GiB) (a coarse bound because fex does not link libc) and declines stubs, and libc's handler only rewrites ordered loads/stores (next entry); it is named on stderr and the process dies;
  - an ordered access (STLUR/LDAPUR, STLR/LDAR/LDAPR) copied into a displaced-access stub that crosses a 16-byte boundary (ASTRO BOT: `STLURH` on a heap pointer ending 0xfcf) is rewritten by libc's displaced handler to FEX's HalfBarrier form (DMB ISH + STUR, LDUR + DMB ISHLD) in a NOP slot the stub reserves, for good (a022e3426, fex fixture `displaced-unaligned`). As with FEX's own backpatch, accesses that cross 16 bytes are then not single-copy atomic (x86 would make them so unless they cross a cache line; within 16 bytes FEAT_LSE2 keeps plain accesses atomic), and the stub always takes the half barrier (FEX's NonAtomic mode is not mirrored);
  - macOS raises protection faults and alignment faults (an ordered access or atomic crossing 16 bytes) as the same SIGBUS/BUS_ADRALN; only the ESR's fault status (0b100001) tells them apart. The write watch now chains alignment faults (it used to claim them on writable watched pages and retry forever, ASTRO BOT); the displaced handler and FEX's unaligned handler still decide by address range and the faulting instruction, not by the ESR;
  - two threads faulting on one translated site race its patch: the later handler finds the branch to the site's stub and runs the recorded access ([GuestDisplaced.cpp](../../core/libs/prx/libc/src/GuestDisplaced.cpp) `Redirect`). A far site (BRK return) is not patched, so it has no such race;
  - a guest access to an unmapped part of the window faults at the alias address, so crash reports show `guest | 1<<40`;
  - fixed guest mappings in the PS5 system-reserved range 0x7FFFFC000-0x1000000000 are refused even though the tail and the commpage guard there are displaced (as on every host); the console libkernel address 0x8000004ea is served by a FEX thunk (D32). A mapping across the shared cache's end or across 448 GiB throws ("straddles");
  - the alias window (~435 GiB of PROT_NONE) counts against `RLIMIT_DATA`: macOS refuses a data limit below the reserved address space.
- On macOS the [guest address space arena](../../core/libs/prx/libc/src/GuestArena.cpp) reserves the PS5 layout from 8 GiB to 0xFC_0000_0000 around what the host mapped there first, as on Linux. On arm64 that is a lot: the dyld shared region from 6 to 63 GiB, the commpage nesting region to 64 GiB, the GPU carveout from 64 to 448 GiB and malloc's regions between 448 and 512 GiB (measured on an M3, macOS 27.0.1); about 536 GiB stays for first-fit placement. Fixed mappings in the shared region's tail, the commpage guard and the GPU carveout are displaced to an alias (D31, D33, entry above); first fit never lands there. One that overlaps the other host regions (the shared cache itself, malloc's regions) throws (`fixed guest mapping overlaps a host region in the guest arena`), and one below 4 GiB throws naming `__PAGEZERO` ([DirectMemory.cpp](../../core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp)), since macOS keeps the low 4 GiB unmapped on arm64. Guest mappings, the arena heap and the AMM ranges of [libSceAmpr](../../core/libs/prx/libkernel/Apr/src/Apr.cpp) are placed in the arena as on Linux; the GPU driver's page-state cache is sized for it but only filled on Windows.
- On macOS, the CPU libraries emulate Linux and FreeBSD behaviour the host lacks; known gaps:
  - [EVFILT_VNODE](../../core/libs/prx/libkernel/Equeue/src/specifics/macos/HostVnodeWatch.cpp) watches a path with a host kqueue vnode watch and rereads the directory on each event: a file moved into a watched directory reads as a create; removing one of several hard links reads as a move-out; a moved-in entry is told from a created one by its birthtime against CLOCK_REALTIME; each directory event rereads the whole directory, so changes that cancel out between two reads collapse into one NOTE_WRITE; a watch outlives the deletion of its path;
  - guest `poll` on a socket asking for urgent data (POLLPRI or POLLRDBAND) waits in 5 ms poll slices and reads select's exception set after each, because XNU's poll never reports a pending out-of-band byte ([Udp.cpp](../../core/libs/prx/libkernel/Socket/src/Udp.cpp)); such a socket numbered at or above FD_SETSIZE throws. The kernel socket poll (`GuestSockets::Poll`) still asks the host poll for POLLPRI and so never sees urgent data;
  - `statvfs` ([PathStatistics.cpp](../../core/libs/prx/libSceLibcInternal/PathStatistics.cpp)) has no O_PATH: it opens a readable file or directory for events only (O_EVTONLY) and otherwise (no read permission, FIFO, socket, device) its parent directory, which is on the same volume; an unreadable mount point throws;
  - `mktime` retries a date before about 1570, where macOS mktime fails, 400 years at a time later in the Gregorian cycle ([Time.cpp](../../core/libs/prx/libc/src/Time.cpp)), so the local zone's rules of that later date apply;
  - JIT shared memory ([Jit.cpp](../../core/libs/prx/libkernel/DirectMemory/Jit.cpp)) is an unlinked temporary file (no memfd); the executable view is a host mapping that the runner's translator reads, never host-executable code;
  - `fcntl` keeps O_DIRECT only in the guest's descriptor flags: macOS has no O_DIRECT status flag (uncached I/O is the per-descriptor F_NOCACHE, which cannot be read back), so a descriptor inherited from the host never shows it ([DescriptorControl.cpp](../../core/libs/prx/libkernel/File/src/DescriptorControl.cpp));
  - `sceKernelGetModuleList`, `sceKernelGetModuleInfo` and their `2` variants list the images [dl_iterate_phdr](../../core/libs/prx/libc/src/specifics/macos/GuestImages.cpp) reports and key a dyld image by its Mach-O header (as `sceKernelGetModuleInfoFromAddr` does) and a runner-mapped image by its first PT_LOAD address ([ModuleInfo.cpp](../../core/libs/prx/libkernel/Module/src/ModuleInfo.cpp)); on macOS a `dlopen` handle is not the Mach-O header, so a module opened by `sceKernelLoadStartModule` gets a second handle from these lists;
  - `sceSystemServiceLoadExec` re-executes the process image as on Linux, but throws under the arm64 runner, whose process image is the runner and not the title ([Export.cpp](../../core/libs/prx/libSceSystemService/Export.cpp));
  - an exception thrown on a libkernel host thread (an expired ITIMER_REAL with a guest SIGALRM handler, [Signals.cpp](../../core/libs/prx/libkernel/System/src/Signals.cpp)) ends in libc++abi's terminate, not in the handler the guest set with `std::set_terminate`: on Linux libc's exception runtime interposes the host's C++ ABI, on macOS it does not (`guest_itimer` checks the host terminate handler there). The same holds for a refusal thrown out of a `noexcept` export, such as `mmap` of an app0.zar file (`guest_kernel_app_archive_mmap` checks the host handler on macOS);
  - acosf of an argument outside [-1, 1] returns the x86 default NaN (0xffc00000) as the console does, not arm64's positive default NaN ([Math.cpp](../../core/libs/prx/libc/src/Math.cpp)); other float exports return whatever NaN the host produces;
  - <a id="macos-native-fiber-tests"></a>guest fibers on arm64 switch through the runner's FEX bridge ([Export.cpp](../../core/libs/prx/libSceFiber/Export.cpp)), so native arm64 test binaries cannot run them: `fiber_tests` and upstream's `agc_driver_gpu_map_on_fiber` (a GPU mapping imported from an 8 KiB fiber stack) are not built on arm64; the driver's short-stack hand-off itself is shared code, unverified on a fiber here.
- On arm64 hosts the guest's `long double` is x87 extended precision while the host's is a `double` ([X87Extended.hpp](../../core/libs/prx/libc/include/X87Extended.hpp)): `printf` with `L` conversions, `strtold`, `wcstold`, `__signbitl` and `swscanf_s` with `L` conversions ([ScanningWide.cpp](../../core/libs/prx/libc/src/ScanningWide.cpp)) handle the x87 value in software, and `scanf` with `L` conversions ([Formatting.cpp](../../core/libs/prx/libc/src/Formatting.cpp), [WindowsScanning.hpp](../../core/libs/prx/libc/include/WindowsScanning.hpp)) throws. The [math exports](../../core/libs/prx/libc/src/Math.cpp) `acosl`, `asinl`, `atanl`, `sinl`, `cosl`, `tanl`, `sinhl`, `coshl`, `tanhl`, `expl`, `exp2l`, `logl`, `log10l`, `powl`, `ldexpl`, `truncl`, `frexpl`, `llroundl` and `nearbyintl` take and return the host's `long double`, a `double` on arm64: the [bridge](../../core/fex/src/Bridge.cpp) converts the guest's x87 arguments to doubles (rounding to nearest even) and the results back, so a guest gets double precision, not the 64-bit significand the console's msun ld80 code gives, and the guest's x87 rounding control is ignored; `guest_math` checks them on x86-64 only, the `abi-long-double` fixture through the runner.
- [libkernel_sys on titles](../../core/fex/src/GuestProgram.cpp) (aps5-fex) - the runner opens libkernel_sys.prx for every title, so POSIX calls the console's libkernel exports but AnyPS5 keeps in libkernel_sys resolve; names only libkernel_sys should export would resolve for libkernel importers too
- The arm64 runner [aps5-fex](../../core/fex/src/GuestCpu.cpp) runs guest code through FEXCore from [3rdparty/FEX](../../3rdparty/FEX): Madeira's FEX at its last MIT-licensed commit with fifteen later FEX-Emu fixes, but without FEX-Emu's other changes since FEX-2607, among them its code cache. Under it:
  - a library that calls a function pointer the guest gave it reaches guest code through a fault, which costs microseconds per call, unless the pointer's callback shape is one positional mapping gets wrong (floats past the registers, a hidden result, `long double`...): the [bridge](../../core/fex/src/Bridge.cpp) then swaps it for a thunk from a static table of 4,096 ([GuestCall.cpp](../../core/fex/src/GuestCall.cpp)) that marshals from the shape; when the table is full the fault path takes over, with positional arguments. Other function pointers are not swapped because a library may hand them back to the guest to run (a fiber's entry becomes its `rip`); a thunk the guest gets back as a function result or a resumed `rip` is mapped to the guest function, one stored in a struct the guest reads is not. libc's `qsort`, `bsearch` and application heap use [CallProgram](../../core/libs/prx/libc/include/ProgramCall.hpp) instead; libSceFont's allocator, libSceNgs2's callbacks, thread entry functions and signal handlers still go through the fault. Function pointers inside structs passed by pointer are not described by the signature table;
  - [longjmp](../../core/libs/prx/libc/src/JumpBuffer.cpp) that would change the MXCSR or the x87 control word throws, as FEXCore's rounding mode does not follow a change of the saved guest state through the unwind hooks; [siglongjmp](../../core/libs/prx/libkernel/System/src/SignalSets.cpp) to another x87 control word and a [fiber switch](../../core/libs/prx/libSceFiber/Export.cpp) to a context with another MXCSR or x87 control word resume the whole machine state instead (as `setcontext` does; fixture `fibers-control`). Resuming a machine state writes the MXCSR's rounding mode, FTZ and DAZ into the host FPCR as FEXCore's LDMXCSR does ([Bridge.cpp](../../core/fex/src/Bridge.cpp) `ApplyMxcsrToHost`); before 2026-10-14 it only stored the MXCSR, so a resumed context computed with the previous rounding mode. Native library code runs under the guest's FPCR (the bridge does not switch it), so a guest rounding mode other than nearest also applies to host math inside library calls. A fiber whose entry function returns ends the process;
  - [getcontext, setcontext](../../core/libs/prx/libkernel/System/src/UserContext.cpp) (libkernel) and [makecontext](../../core/libs/prx/libSceLibcInternal/UserContext.cpp) (libSceLibcInternal) reach the guest's registers through the runner's machine state hooks ([GuestMachineState.hpp](../../core/libs/prx/libc/include/GuestMachineState.hpp)). `getcontext` records the state after its call returns: xmm0-7 as the guest passed them, RFLAGS as FEXCore last stored them (the arithmetic flags are dead at a call), no YMM upper halves. `setcontext` applies the general, xmm, x87 and MXCSR state and RFLAGS through FEXCore; when the call came through the fast bridge path, FEXCore does not reload NZCV after it, so CF, ZF, SF and OF of the resumed context are not restored. A made context starts in x86 code in the runner's stub page, which calls the function and then `Aps5MakecontextFinish_nid_no_patch` (`uc_link` through `setcontext`, or exit). There is no `swapcontext` export (no library defines one); guests build it from `getcontext` and `setcontext`. Without the runner (a host process) they throw after their argument checks;
  - [sceKernelRaiseException](../../core/libs/prx/libkernel/System/src/Exception.cpp) (libkernel) on the calling thread runs the handler with the guest's state at the call (returning 0) and resumes a context the handler changed; on another thread it throws, as stopping a thread inside FEXCore to read its registers is not implemented (M1 package G2);
  - on arm64 the tests `guest_user_context`, `guest_user_context_exit` and `guest_raise_exception` run their host programs' argument checks (which report a skip), then the guest fixtures `context`, `context-exit` and `raise` under the runner ([run_host_and_fixtures.py](../../core/fex/tests/run_host_and_fixtures.py)); `guest_signal_sets` checks only the signal set operations: a host caller has no bridge hooks for `sigsetjmp` and `siglongjmp`;
  - the [bridge](../../core/fex/src/Bridge.cpp) passes arguments by register position unless the signature table that [gen_bridge_signatures.py](../../core/fex/tools/gen_bridge_signatures.py) derives from the library sources at build time (`APS5_FEX_BRIDGE_SIGNATURES`, on by default) says that is wrong for the export; those are marshalled from the per-value layouts it computes for both conventions. A variadic export's variable arguments are read from the guest's `va_list` only for the exports in `VariadicExports`; a variadic export whose fixed arguments need marshalling would be passed positionally (none today). An export the table does not know (a library built without the table) is positional, with eight stack slots;
  - a guest thread's x86 frame chain under FEX ends at the bridge's callback frame (whose return address is the translator's callback return), not at the zero record (rbp and return address both 0) that [Thread.cpp](../../core/libs/prx/libkernel/Pthread/src/Thread.cpp)'s `Aps5CallGuestEntry_nid_no_patch` builds on x86-64 hosts; on arm64 that function builds the same record for the native frame chain (test `guest_pthread_frame_chain`), which the translated guest does not see;
  - `sceKernelLoadStartModule` opens only the modules the executable names, which the [runner](../../core/fex/src/GuestProgram.cpp) loads at start;
  - the runner maps every image segment readable and writable and registers the image's pages with libc's registry ([GuestImages.cpp](../../core/libs/prx/libc/src/specifics/macos/GuestImages.cpp)) at 16 KiB granularity: segments that share a page (an ELF linked for 4 KiB pages) give it the union of their access, and `sceKernelQueryMemoryProtection` reports all image memory, data included, as executable. A guest `PROT_CPU_EXEC` mapping is only readable on the host ([LinuxProtFromSce](../../core/libs/prx/libkernel/DirectMemory/DirectMemory.cpp)): FEXCore reads guest code and never runs it, and a native call into guest code must fault into the runner;
  - `sceKernelDlsym` and `dlsym` hand the guest the [bridge's](../../core/fex/src/Bridge.cpp) x86 stub for a native function and the address of native data, and never a symbol of a macOS system library; handle 0 searches the native libraries but not the exports of the guest executable or its modules;
  - guest signal handlers, and C++ exceptions that unwind through a host frame between guest frames, are not supported;
  - the [microbenchmarks](../../core/fex/tests/run_fex_bench.py) cannot keep a thread on the performance cores: macOS has no thread affinity, and with `APS5_FEX_QOS=user-interactive` both the native program and the runner ran at the default priority (31) when started outside the foreground app, so the driver also reports the timing thread's CPU time. The native side of `bridge_qsort` is a copy of libc's heapsort `qsort` ([bench_native.cpp](../../core/fex/tests/bench/bench_native.cpp), [FileAndHeap.cpp](../../core/libs/prx/libc/src/FileAndHeap.cpp)) and has to follow it. [APS5_FEX_CONFIG](../../core/fex/src/Options.cpp) checks option names but not values;
  - RDTSCP and RDPID give processor 0, vector loads and stores are not ordered as x86 orders them (FEXCore's default), and flush-to-zero and denormals-are-zero as separate controls were checked only on an M3 Pro, whose cores have FEAT_AFP;
  - an atomic, and with FEXCore's TSO emulation any integer load or store, that crosses a 16-byte granule raises SIGBUS (BUS_ADRALN) on Apple cores, and the runner has no unaligned-access handler for it yet, so the process dies; 69 of FEX's ASM tests are [known failures](../../core/fex/tests/asm/Known_Failures_macos) for it;
  - FEXCore compiles a block into a temporary buffer whose size it estimates and expects the frontend's SIGSEGV handler to restart the compilation with more space when the block reaches the buffer's guard page (FEX's LinuxEmulation `SignalDelegator::HandleFrontendSIGSEGV`). The runner does not, so a block that outgrows the estimate crashes it (`FEX_bugs/CodeBufferOverflow.asm`). FEXCore also cannot protect the last page of a code buffer in the runner's pool: it uses 4 KiB pages and logs "Failed to mprotect last page of code buffer";
  - the [runner's syscall handler](../../core/fex/src/GuestCpu.cpp) implements neither `MarkGuestExecutableRange` nor `InvalidateGuestCodeRange`, so FEXCore's default self-modifying-code detection (`SMCChecks` MTRACK) never sees a guest write to compiled code and the stale code runs, and with `SMCChecks=full` a changed block is found but never dropped, so the guest loops. The bare guest of the ASM tests implements the invalidation;
  - a guest thread's GDT has 32 entries (`GuestThread`), and FEXCore reads the entry of any selector moved into ES, SS or DS without a bounds check where x86 raises #GP, so such a move reads past the table (`Primary/Primary_8C.asm`);
  - the runner's host features leave out CLZERO, which Zen 2 has and FEXCore could run with the M3's 64-byte DC ZVA, and RDRAND and RDSEED are missing because the M3 has no FEAT_RNG; their ASM tests are skipped;
  - the per-instruction oracle, FEX's ASM tests under [aps5-fex-asm](../../core/fex/tests/asm/AsmHarness.cpp), runs 2,194 of the 2,222 64-bit tests: [prepare_asm_tests.py](../../core/fex/tests/asm/prepare_asm_tests.py) moves their low addresses above 4 GiB, and the 18 tests in [Disabled_Tests_macos](../../core/fex/tests/asm/Disabled_Tests_macos) use 32-bit addresses or Linux syscalls or, with nasm 3, an encoding the recorded results do not apply to (nasm 3 assembles 26 tests differently from the nasm 2 FEX recorded them with; only `smsw` changes meaning, and `APS5_FEX_ASM_NASM` selects another nasm). Like FEX's harness it compares registers only, not memory.
  - the guest-thread sampler ([GuestSampler.cpp](../../core/fex/src/GuestSampler.cpp), `APS5_FEX_SAMPLE`) maps a host PC to the exact guest RIP only inside the block a thread is running (FEX's per-block RIP entries). In a displaced-access stub, the dispatcher, a signal handler past `_sigtramp`'s first instruction or host code it reports the RIP FEX stored when the thread last left JIT code, and the guest registers are FEX's spilled copy, which can be stale. Import stubs are named by NID only.

- <a id="guest-own-guards"></a>A guest image that exports its own `__cxa_guard_acquire`, `__cxa_guard_release` and `__cxa_guard_abort` (homebrew linking libc++abi built with `_LIBCXXABI_HAS_NO_THREADS`, such as oops-apps titles) has all three redirected by aps5-fex to libc's thread-safe guards through FEX thunks at the exported addresses ([GuestGuards.cpp](../../core/fex/src/GuestGuards.cpp), D48; `APS5_GUEST_GUARDS=0` turns it off). Known gaps: only images loaded at startup are redirected (not modules loaded later with sceKernelLoadStartModule); an image that exports only some of the three is left alone; code reaching a guard function's body other than at its entry (a tail jump into its middle, or a block compiled before the thunk) runs the guest's own version; libc's guard waits by spinning with `yield` (a long initialiser costs the waiting threads CPU); and a guard taken by one thread and released by another terminates, as libc's guards always did.

- <a id="fex-cpuid-macos"></a>On macOS aps5-fex gives FEX one MIDR per logical CPU, all `0x61000000` (Apple, part 0), because user code cannot read MIDR_EL1 there ([GuestCpu.cpp](../../core/fex/src/GuestCpu.cpp) `HostFeatures`, D50). So CPUID's brand string (leaves 0x80000002-0x80000004) reads "Apple Silicon" rather than a PS5's AMD name, and FEX never reports a hybrid (big/little) CPU although the M-series has performance and efficiency cores. FEX's CPU index for the per-CPU leaves is always 0 on macOS (its getcpu fallback).

### Metal device (macOS)

Behaviour of the Metal device ([MetalDevice.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/MetalDevice.mm), work package D1) and its guest memory ([GuestBufferMemory.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/GuestBufferMemory.mm), D3) where it still differs from upstream's VulkanDevice. Everything here is correct but conservative; none of it is a silent stub.

- Two kinds of guest-memory wrappers: labels, fills and copies use the host imports (upstream's HostImportFor, no-copy buffers per registered allocation run, kept until the registry changes); dispatch V# ranges, GDS, indirect arguments and the BDA page table use the device's own page wrappers (any readable, non-executable memory, static `__DATA` included), dropped whenever the recorder is idle and re-made on the next use. Upstream copies unimported V# ranges into buffers with a write-back; the Metal device binds them in place. Unifying both on the imports (and pre-wiring large allocations off the critical path) is D3 work Since D42 a run longer than 1 GiB is imported in aligned 1 GiB pieces (Metal wires every no-copy import in full at its first GPU use, so a single import of a 7.8 GiB run would wire 7.8 GiB): a resource that crosses a piece boundary is not served by an import (HostImportFor returns none; page wrapper or copy), and the address-space build falls back to a mirror of the whole range when one of its pieces is refused by the wired budget (3/8 of RAM).
- <a id="metal-residency-lock"></a>Residency sets and queue commits share one process-wide lock (MetalResidency.h, DECISIONS D44): the debug layer's commit walks the attached sets while the release thread changes them. Removed allocations live until the next queue commit returned (or `Drain`), so a removed no-copy import outlives its `RetiredImport` by up to one commit. The lock serializes set changes of all devices and queues; contention has not been measured (one queue per device today).
- <a id="metal-host-import-window"></a>Host imports join adjacent allocations only over whole aligned 8 MiB windows (upstream a94730373; D44). A heap growing in small ranges is imported range by range until its window fills, so such a heap carries many small imports (SuperTuxKart: ~3400 live imports of 16 KiB); `HostImportFor` misses still take a registry lease (O(registered ranges)) per call. Allocations that each cross a window boundary and are adjacent and compatible join one import (D65), so a surface spanning two large allocations has one.
- <a id="metal-d3-import-watch"></a>Host imports are compared, never write-watched, and not probed: the macOS write watch is mprotect-based and GPU stores through a no-copy buffer bypass it, and upstream's probe (`ProbeImportWriteProtection`) would have the GPU store into write-protected pages on purpose (DECISIONS D19). Unwatching also lifts the protection from imported pages. A probe (or a watch that GPU stores provably mark) would let imported ranges skip the comparisons
- BDA page table: the registered allocations plus, per dispatch, every bound V# (Write when the shader stores to it), GDS and the captured snapshots (in place, or their captured bytes when the pages cannot be wrapped), made disjoint by `Metal::DisjointRanges`. Registered ranges that cannot be wrapped (executable or unmapped pages) are left out and fault `Unmapped`; no mirrors. The registry lease is held by in-flight batches only and no pin waiter is installed, so a guest unmap of a leased range yields until the batch is reaped
- <a id="metal-bda-wired-budget"></a>BDA page table under the wired budgets (DECISIONS D52): the registered allocations enter the table only through host imports (a long one piece by piece, the D42 1 GiB windows) or, when not imported, through page wrappers while all the device's wrappers stay under `APS5_BDA_WRAP_MIB` (1 GiB). What neither budget admits is left out (ASTRO BOT: 6.2 GiB of 12.6 GiB) and an access there records an Unmapped fault and reads 0, where the guest would read its memory: the GPU cannot wire all of a 12+ GiB guest on a 16 GB Mac. No residency on demand (fault and retry), no choice of which pieces to keep by use (the table takes allocations in address order), and an access crossing a 1 GiB piece boundary of one allocation is split over two ranges (each a separate import).
- <a id="metal-untracked-storage"></a>Storage images over memory outside the write watch (DECISIONS D57; on Metal every host import unwatches its range) compare against saved guest bytes. An image a fill or buffer copy supersedes keeps (or saves) them. Still refused (upstream's behaviour): an image uploaded while its memory was watched (saved bytes dropped) whose range an import later unwatches while results are pending, and a write-back after a DCC key clear over untracked memory; neither is seen in ASTRO BOT yet. libkernel's aliased direct mappings leave the watch in libc directly (APS5_TRACE_LEAVING_WATCH names every unregistration).
- <a id="metal-occlusion-passes"></a>Occlusion counting on the Metal draw path: each new pass takes its counter slot before it begins (Recorder::PrepareSamplePass, D57), one slot per pass, a fresh 128-slot visibility buffer when a batch's is used up.
- Device-memory LDS arena: one arena per device shared by every dispatch; it grows only while idle (a wait), and a workgroup ended by the loop guard while holding its LDS lock leaves the lock dword set for later dispatches. The 64-bit atomic lock table (MslAbi v2) is one 4 KiB table per device with the same caveat
- GPU faults (BdaAbi fault and written-page records) are read when a batch with dispatches completes and raised at the next `Sync`/`ReapRecorded(serial)`, not at the wait that retired the batch
- `ReplayComputePipeline` (Vulkan pipeline captures) and `DispatchRecipe` throw; `DispatchRecipes()` is false and `PrepareDispatch` only starts the pipeline build on D5's workers
- `agc_driver_store_idle_results` aborts at exit after its check fails: `Driver::~Driver` locks `GuestMemory::GpuMutex()`, a function-local static destroyed earlier (upstream order of statics; only reached when a test returns without `AgcDriverShutdown`)
- <a id="metal-shared-queue"></a>All VulkanDevices on one MTLDevice commit on one shared MTL4 queue (DECISIONS D43): objects keyed by the MTLDevice (host imports, image mirrors, unit shadows) are used by a replacing device, which upstream avoids by resetting them per VkDevice. The replaced device stays alive until shutdown and its residency sets stay on the shared queue; a teardown of either device while the other has work in flight would destroy the shared imports (`ClearHostImports` is keyed by the MTLDevice).
- <a id="metal-first-frame-compile"></a>MSL libraries compile synchronously on the queue worker when a draw first needs them. DECISIONS D54 shrank the translation (UI Lab's 7.7 MB fragment program: 3.4 MB, cold library 17.2 s -> 2.1 s; Showcase 1.0.1's largest 884 -> 405 KB) and D55 keeps every library source and compiles the stored ones at device creation, so a second run finds them compiled (and in the system cache). A first cold run can still exceed a guest's bound (ps5-opengl SDK <= 1.0.1 gives a submission 2 s): see PROGRESS SHD7 for UI Lab and Showcase 1.0.1. Remaining size levers: (1) wave64 compute at two lanes per invocation emits every value twice: DECISIONS D62 runs wave64 compute at one lane per invocation where the wave's other lanes do not matter or a one-wave threadgroup can exchange through threadgroup memory (ASTRO BOT's MSL 1.23 -> 0.98 GB, largest library 8.8 -> 4.5 MB; see [metal-wave64-lane-local](#metal-wave64-lane-local) for what stays at two lanes); (2) RDNA NaN emulation (`nanResultF32`) is about half of what is left (UI Lab 3.4 -> 1.0 MB and 1.4 -> 0.4 s without it in an experiment), needed because the GPU's NaN results differ; DECISIONS D63 drops it where no NaN can reach (see [metal-nan-test-elimination](#metal-nan-test-elimination)); (3) indentation of deep structured control flow (55% of ASTRO's largest library) costs no compile time (DECISIONS D63, measured). Not done: draw skipping while a pipeline compiles (opt-in, wrong first frames; D56). The library store (D55) is shared by every title of a shader cache directory (no title id in the driver), so a prewarm can compile another title's libraries

- <a id="metal-wave64-lane-local"></a>(DECISIONS D62) Wave64 compute keeps two guest lanes per invocation (every value emitted twice) when: v_readlane/v_readfirstlane or exact ballots or undecidable wave-mask branches sit in a workgroup of more than one wave (barriers would have to be reached by every wave; ASTRO BOT: 91 MB of its 977 MB of MSL), ds_append/consume, half-wave reads (DPP, permlane16, swizzle, bpermute) in a partial wave, LDS accesses not separated by s_barrier in multi-wave workgroups, more than 256 invocations per workgroup (MslLaneLocalMaxThreads, so the doubled host threadgroup stays within pipelines' maxTotalThreadsPerThreadgroup; not measured per pipeline), or a 512-byte exchange buffer that would not fit beside LDS in threadgroup memory. One-wave threadgroups pay a threadgroup barrier per vote, exact ballot or lane read (not measured at run time). The lane mapping (guest lane = thread index & 63, SIMD group = 32 consecutive threads) is the two-half layout's assumption, checked by agc_metal_wave64_lane_local for one-dimensional workgroups only. Shader clock reads (s_memtime) at one lane per invocation are per SIMD group, so the two halves of a wave may read different times. Each invocation reads scalar memory itself (as at two lanes per invocation): a guest that polls memory another queue writes can see different values in different invocations of one wave, and with threadgroup exchanges a branch on such a value could split the threadgroup at a barrier.
- <a id="metal-nan-test-elimination"></a>(DECISIONS D63) NanTestEliminator proves "never a NaN" only for constants, integer conversions, clamps, abs/neg, min/max, floor/ceil/trunc/fract, add/sub/mul/fma under magnitude bounds, sqrt/rsqrt of values never below zero, rcp and exp2; everything read from memory, inputs, transcendentals other than exp2, f16/f64 conversions and loop-carried phis count as possibly NaN, so most NaN tests of title shaders stay (they compute on loaded data).

### Metal images, samplers and pipelines (macOS)
- [The pipeline archive](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/PipelineCache.mm) flushes its MTL4 serializer only while no compile captures into it (a shared/exclusive gate): a save waits for the compiles in flight, and new compiles wait for the save. Whether Metal's serializer tolerates a flush during capture at all is not documented; it crashed (`dispatch_data_create_map(NULL)` under `-[_MTLBinaryArchive newArchiverIdWithBinaryKey:...]`, ASTRO BOT).

Work packages D4/D5 ([MetalImages.h](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/MetalImages.h), [MetalTextures.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/MetalTextures.mm), [MetalPipelineCache.h](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/MetalPipelineCache.h)) and B4 ([MslImage.cpp](../../core/shader/recompiler/MetalBackend/src/MslImage.cpp)).

- <a id="metal-d4-image-paths"></a>One image path: the upstream twins (Texture.mm, ShaderResources.mm, UnitShadow.mm, TextureDetiler.mm with MSL kernels; the pending/live storage registries, texture and resource caches). The bring-up path of MetalTextures.mm (per-dispatch CPU uploads, write-back at batch completion, `APS5_METAL_UPSTREAM_IMAGES=0`) was deleted on 2026-10-13 after the upstream path matched or beat it on G1-G4 (M2_DESIGN "SHD3 results"). The CPU (de)tiler stays for the draw path's `APS5_NO_RESIDENT_TARGETS` debug mode and its tests. Multisampled guest images are refused (D4)
- <a id="metal-d4-cpu-detile"></a>CPU detile on the bring-up path (MetalTextureDetiler.mm) waits for nothing but runs on the submission thread; the upstream path detiles with the MSL kernels (TextureDetiler.mm) recorded into the batch. Three-channel 32-bit formats (72-74) have no Metal pixel format: the shim refuses them
- <a id="metal-d5-pipeline-archive"></a>Pipeline archive: the MTL4Archive is not used under `MTL_SHADER_VALIDATION=1`. Archives serialized while shader validation instruments the pipelines do not load again on macOS 27.0.1 ("deployment target for architecture applegpu_g15g found in archive ... is not compatible with current OS"), and lookups would hand out uninstrumented pipelines. The archive holds pipelines only: libraries are compiled again in every process (the OS Metal cache serves them in milliseconds); the `MTLBinaryArchive` fallback of M2_DESIGN §7 is not implemented (MTL4Archive works) Persistence (DECISIONS D51): `serializeAsArchiveAndFlushToURL` empties the serializer, so every save first replays the pipelines an earlier save flushed and the archive's hits through the compiler with lookup archives (no compile; cost per save grows with the pipelines of the process, saves are spaced by 1 s or 4x the last save); each process writes its own archive generation and loads the newest, so a pipeline of an older generation that this process neither hit nor compiled is dropped when the next process deletes the older generation. Metal resolves a lookup archive through its file: the archive file a process loaded is never rewritten while the process runs.
- <a id="metal-d5-sampler-reduction"></a>Sampler min/max reduction: `MTLSamplerDescriptor.reductionMode` is ignored on the M3 under macOS 27.0.1 (`agc_metal_sampler_reduction`: Minimum and Maximum return the weighted average, through argument buffers and bound directly), and some combinations fail Metal's descriptor validation. The sampler filters normally and the shader reads the 2x2 footprint through it and reduces it (`PipelineSpecialization::ReductionBase`, explicit-LOD sampling of float 1D/2D/2D-array views). Gradient and implicit-LOD sampling through a reducing sampler fall back to plain filtering
- <a id="metal-d4-xor-4kb"></a>SW_4KB_S_X/D_X: the CPU detiler applies the XOR equations to the whole element coordinates, as Graphics/shaders/TextureDetile.comp does; ColorTargetLayout applies them to the in-block bits only. The two upstream tilers disagree for surfaces larger than one block, and no hardware measurement decides it yet (`agc_metal_texture_detile` checks only the modes they agree on)
- <a id="metal-b4-images"></a>MSL images: stores and atomics through bindless image tables are refused (as on the SPIR-V path); BY2/BY4 and packed loads, conversions, sRGB decode, emulated depth compare, BVH intersection and bindless sampling follow SpirvImageEmitter.cpp. 64-bit image atomics run under the atomicLocks table (one elected lane per SIMD group and round), committed with the texture's atomic max/min
- <a id="metal-ms-storage"></a>Multisampled storage images are emulated (DECISIONS D22, MslAbi v6): Metal shaders cannot write `texture2d_ms`, so the storage heaps of the 2D MSAA and 2D MSAA array dimensions are `texture2d_array<T, access::read_write>` of layers * samples slices (sample s of layer l at slice l * samples + s; [MslImage.cpp](../../core/shader/recompiler/MetalBackend/src/MslImage.cpp) `EmulatedMultisampleCoord`); stores, 32-bit atomics and lock-table 64-bit atomics use it, the sample count is function constant `PipelineSpecialization::SampleCountBase + resource` (the binding plan supplies 1 << T# LAST_LEVEL), and the MSL binding plan gives such views the `Image2DArray` shape. Verified: `agc_metal_msl_ms_storage` (stores and 32-bit atomics dispatched on 2-layer, 4-sample backings; the 64-bit atomic is compile-only) and the four `agc_driver_prepared_shaders*` tests. Gaps and costs: (1) no guest multisampled *storage* image reaches a binding yet: storage bindings still go through `DecodeTextureResource`, which rejects T# types 14/15 on every platform (upstream gap, Vulkan too; sampled-class MSAA T#s are bound since D27, [metal-msaa](#metal-msaa)), so only the placeholders (single-sample 1-slice 2D arrays, PlaceholderImages.mm) are ever bound. When guest MSAA images land, TEX must bind one shadow 2D array per multisampled image (same format, layers * samples slices) and keep it coherent with the real multisampled texture used for sampling, resolves and rendering, tracked by dirty state: multisampled to shadow with a compute kernel that reads `texture2d_ms` per sample before storage access; shadow to multisampled with a render pass that writes each sample (`[[sample_id]]` fragment, per-sample shading) before those uses, because compute cannot write it. No aliasing route exists: a 2DMultisample texture can be viewed only as 2DMultisample/2DMultisampleArray, and heap aliasing has an undefined sample layout. (2) Reads and size queries of multisampled images are sampled-class resources (ResourceTracker), which still have no descriptor shape (upstream gap); the emitter refuses a multisampled storage read/query instead of emitting it. (3) Every distinct sample count is its own pipeline specialization. (4) The metadata path for table (indirect) images is emitted but unreachable while table stores and atomics are refused ([MSL images](#metal-b4-images)). (5) The Metal device does not advertise `CapabilityStorageImageMultisample` yet (MetalDevice.mm, DRAW2), so a title's multisampled storage shader still fails preparation with "storage image multisampling is unavailable on the target device"; the tests add the capability to their target **Update (DECISIONS D28):** gaps (1) and (2) are closed for targets the driver rendered: a guest MSAA storage T# binds the target's storage shadow (MultisampleTarget.mm MultisampleStorageTexture), kept coherent in recording order (host image to shadow by a compute kernel before a storage use when the host image is newer; shadow to host image by one per-sample render pass per slice before the next draw, sampled view or resolve; MetalVulkanImages.mm CopyMultisampleToStorage/CopyStorageToMultisample), verified by `agc_metal_msaa_storage` (4x and emulated 8x stores, 4x 32-bit atomics, one copy each way); sampled reads and size queries of MSAA images are emitted (MslAbi v9). Remaining: 64-bit atomics on MSAA storage throw; the shadow uses the target's pixel format, so a storage T# in another format throws; the shadow-to-host pass rewrites every sample of the target, whatever the stores touched.
- <a id="metal-d4-vulkan-shim"></a>The texture twins keep upstream's Vulkan-shaped code: MetalVulkanImages.mm carries the image calls on Metal (VkImage/VkImageView/VkSampler hold CF-retained Metal objects, descriptor sets are tokens and their writes become MslAbi table entries, image layouts do not exist, barriers are stream barriers). Image view min-LOD clamps (VK_EXT_image_view_min_lod) have no Metal counterpart: `imageViewMinLod` stays false and such textures are refused as upstream does without the extension
- <a id="metal-texture-host-memory-fallback"></a>Upstream #4108 (`Context::DeviceMemoryType`) places images in host memory when the device-local heap budget is exhausted; Metal textures own their memory on unified memory and have no such fallback, so a failed texture allocation still throws (Texture.mm, upsync 0f2683cb7)

### Metal draws and presentation (macOS)
- <a id="metal-list-restart"></a>(DECISIONS D53) Indexed point/line/triangle lists with primitive restart (PrimitiveListRestart true) are expanded on the CPU (MetalDraw.mm `listRestart`): a restart index ends the current primitive and drops its incomplete vertices. Every such draw reads its indices on the CPU, also when they hold no restart index; mesh (NGG) list draws that hold a restart index throw (the mesh function has no list restart).
- <a id="metal-texel-offset-range"></a>(DECISIONS D53) Texel offsets computed at run time go to MSL's sample/gather offset argument (the Metal target reports nonConstantImageOffsets). Metal is reported to clamp offsets to [-8, 7] (not measured here); RDNA2's fields are 6-bit ([-32, 31]), so a larger offset samples elsewhere than on the PS5.
- <a id="metal-mip-overflow"></a>(DECISIONS D64) A guest descriptor may declare more mip levels than its dimensions allow (radeonsi's block views of compressed textures); the host image holds the allowed levels and each further level is a 1x1 texture of its own (views and copies use it). A view starting at a host level stops at the host's last level (sampling past it reads that level, not the further 1x1 levels), and clears past the host's levels are skipped.

- <a id="metal-d6-bring-up-draws"></a>The Metal draw path (specifics/macos/src/MetalDraw.mm) is new code beside the device, not a twin of Graphics/src/Draw.cpp (which stays compiled and unreachable on Metal, like Pipeline.cpp and MultisampleTarget.cpp): no draw recipes (DrawFromRecipe always rebuilds; agc_driver_depth_bias_per_face's recipe steps run as fresh draws on Metal, as VertexTargetRangeTwin's do), no resource-cache templates, no draw snapshots of guest buffers (vertex, index and indirect data are read in place through wrappers or host imports), no PrebuildGraphicsLibraries. - <a id="metal-d6-targets"></a>Color targets: linear ones are textures over the guest memory itself (newTextureWithDescriptor on the wrapper/import; offset and pitch must meet minimumLinearTextureAlignmentForPixelFormat, else the draw throws); tiled ones are private textures loaded by a CPU detile (ColorTargetLayout) when their pass begins and written back by a CPU retile when the batch completes, so a CPU read of a tiled target waits for its batch. - <a id="metal-d6-indirect"></a>Indirect draws read their records on the CPU (DrawIndirectSupport reports no GPU path); multi-draw-indirect-count reads the count on the CPU too. GPU indirect (Metal's argument layouts match Vulkan's) and ICB-based count draws are M4 work
- <a id="metal-d6-cmask"></a>CMASK fast clears are materialized on the CPU (fill the cleared 8x8 tiles in guest memory, expand the CMASK) before a draw or a fast-clear eliminate, after syncing GPU work over the target; upstream's GPU CmaskClear pass is not used
- <a id="metal-d6-depth-sampling"></a>Depth surfaces are GPU-only as upstream. ### Metal skips (macOS)

- <a id="metal-linux-udmabuf"></a>Linux udmabuf host imports: `agc_host_import_sparse` (tests/HostImportSparseDmaBuf.cpp) and `agc_driver_sparse_dma_buf_import` (tests/execution/SparseDmaBufImport.cpp) import sparse guest memory through /dev/udmabuf and VK_EXT_external_memory_dma_buf, a Linux kernel API macOS does not have; they skip "udmabuf imports are Linux only" (allowlisted). Facts from the Metal Feature Set Tables and probes on an M3 (Apple9).

- <a id="metal-shader-clock"></a>Shader clock: MSL has no shader or device clock, so `s_memtime` and `s_memrealtime` read an emulated clock ([MslFlowEmitter.cpp](../../core/shader/recompiler/MetalBackend/src/MslFlowEmitter.cpp) `EmitClock`): a device-wide 64-bit count of clock reads in the two words after the 64-bit atomic lock words (`MslAbi::ClockCounterWord`), taken by one elected invocation per SIMD group and broadcast. It is uniform over the wave (over each 32-lane view of a wave64 graphics program, `metal-b6-half-wave`), nonzero and increasing across waves, dispatches and draws, so [ShaderClock.cpp](../../core/libs/prx/libSceAgcDriver/tests/execution/ShaderClock.cpp) (`agc_driver_shader_clock`) runs. It counts reads, not time: elapsed-time measurements and timeouts that a title converts to seconds see one tick per read, and `s_memrealtime` is not in the 100 MHz domain of the CPU-visible GPU clock (`COPY_DATA` `SRC_SEL` 9). When the low word wraps (every 2^32 reads) a concurrent reader can see the old high word once. Without the table (DriverData.atomicLocks 0) the count is the invocation's own.
- <a id="metal-geometry-shaders"></a>Geometry shaders: Metal has none. The barycentric emulation upstream builds as a geometry stage runs as triangle-vertices draws instead ([per-vertex values](#metal-per-vertex-values), D20), and [PixelBarycentricEmulation.cpp](../../core/libs/prx/libSceAgcDriver/tests/execution/PixelBarycentricEmulation.cpp) (`agc_driver_pixel_barycentric_emulation`) runs on Metal without one. - <a id="metal-conservative-rasterization"></a>Conservative rasterization is emulated (DECISIONS D21): the Metal API has none, so draws asking for it run in the triangle-vertices mode (MslAbi v5, `APS5_CONSERVATIVE`; [MslConservative.hpp](../../core/shader/recompiler/MetalBackend/include/MetalBackend/MslConservative.hpp)): the vertex function moves each corner outward by the half-pixel edge offsets and passes the triangle's framebuffer-space vertices flat, the fragment function discards pixels whose square the triangle does not touch (overestimation) or cover (underestimation); degenerate triangles become their half-pixel-grown box tested on the axes they have. `agc_driver_conservative_rasterization` passes (gpu-suite/shd4-conservative, --validation, 2026-10-13). ### MetalBackend ALU and f64 (macOS)

Gaps and costs of the MSL ALU and f64 families ([MslAluMath.cpp](../../core/shader/recompiler/MetalBackend/src/MslAluMath.cpp), [MslFloat64.cpp](../../core/shader/recompiler/MetalBackend/src/MslFloat64.cpp); work package B2 in [M2_DESIGN.md](../mac/M2_DESIGN.md)). Apple GPU facts behind them come from `.mac-work/research/metal-probes/probe_float_b2.swift` (M3, macOS 27.0.1); the helpers are checked against CPU IEEE references by `agc_metal_alu_helpers`. Costs below are dependent chains of 512 operations over 1M threads on the M3 (`probe_alu_cost_b2.swift`), relative to the native f32 operation.

- <a id="metal-alu-f32-denormals"></a>f32 denormals: Apple GPUs flush them to a signed zero in every f32 operation (compares, min/max and floor/ceil included) and detect tininess before rounding. With FLOAT_MODE flushing f32 denormals (the default) the ALU runs native f32 math. The front end flushes operands and results itself except for v_add/v_sub/v_subrev/v_mul/v_fma/v_fmac/v_fmamk/v_fmaak/v_fract/v_floor/v_ceil_f32 and the f32 compares with round to nearest even on Metal (SpirvTarget::float32DenormFlushNative, DECISIONS D54), where the GPU flushes and `aps5_fmul_ftz`/`aps5_fma_ftz` recompute a zero result (a product that rounds up to 2^-126 is kept as RDNA keeps it); `v_min`/`v_max`/`v_med3`, conversions, transcendentals, VOP3P and directed rounding keep the explicit flushes. With FLOAT_MODE keeping f32 denormals (`MslTargetOptions::keepF32Denormals`) add, sub, mul, fma, mad, compares, floor, ceil and fract are exact on bits whenever an operand is denormal or the result is tiny (fast path 2.8x for an add, 3x for an fma). Still flushed in that mode: denormal results of `v_rcp`, `v_rsq`, `v_sqrt`, `v_exp`, `v_log` and `v_sin`/`v_cos` (their denormal operands are flushed by the SpirvBackend's rules anyway)
- <a id="metal-alu-min-max-cost"></a>`v_min`/`v_max`/`v_med3_f32` order operands on their bits (RDNA's NaN and signed-zero rules on denormals the GPU would flush): 3.2x a native `max`. With FLOAT_MODE flushing denormals a float compare plus the zero and NaN rules would do (M4)
- <a id="metal-alu-transcendentals"></a>Transcendentals: `v_rcp_f32`, `v_rsq_f32`, `v_sqrt_f32` and `v_exp_f32` use Metal's precise `1/x`, `rsqrt`, `sqrt` and `exp2`; `v_log_f32` and `v_sin`/`v_cos_f32` add the SpirvBackend's series corrections near 1 and per turn quadrant. Metal's precise functions are within a few ulp, RDNA's within 1 ulp, so a result can differ from the console in the last bits; the hardware-oracle tests pass, but RDNA's approximation tables are not reproduced
- <a id="metal-alu-soft-f64"></a>f64 is IEEE binary64 in software on 64-bit integers (Apple GPUs have no double): exact, but an add costs about 70x a native f32 add, a multiply 85x, a division (restoring long division, 63 steps) 930x; a square root runs a similar 56-step digit loop. `v_dot2_f32_f16` outside its f32 fast path and the f64-based interpolation/`v_fma_mix` rounding go through it. A title with f64-heavy shaders needs a faster division and square root (reciprocal estimate plus integer Newton steps) (M4)
- <a id="metal-alu-contraction"></a>Floating-point contraction is off through `#pragma METAL fp contract(off)` in the Alu prelude chunk, which every ALU float operation requires; float arithmetic another family emits without requiring that chunk gets the compiler's default contraction (MTLMathModeSafe and precise functions are set by the device either way)

### MetalBackend wave, LDS and atomics (macOS)

Gaps and costs of the MSL wave, LDS/GDS and atomic families ([MslWave.cpp](../../core/shader/recompiler/MetalBackend/src/MslWave.cpp), [MslMemory.cpp](../../core/shader/recompiler/MetalBackend/src/MslMemory.cpp); work package B3 in [M2_DESIGN.md](../mac/M2_DESIGN.md)). Checked on the CPU by `agc_metal_msl_wave_lds`.

- <a id="metal-b3-atomics64"></a>64-bit atomics: Apple9 has 64-bit device atomics only as `atomic_max/min` without a result, and no 64-bit threadgroup atomics. Every 64-bit LDS atomic (and every LDS atomic of a program that has one, `SpirvRequirements::ldsLock`) runs as a plain update under the LDS lock dword; every 64-bit buffer/flat/global atomic takes a word of the driver's 4 KiB lock table (`DriverData::atomicLocks`, hashed by address). One elected invocation per SIMD group tries the lock per round, so contended atomics serialise: a wave of 64-bit atomics on one address costs about one lock round per lane. After 2^20 rounds the loop records a LoopLimit fault and gives up instead of hanging. A dispatch without a lock table records the fault and leaves memory unchanged. M4: native `atomic_max/min` for 64-bit umin/umax without a result
- <a id="metal-b3-gds64"></a>64-bit GDS atomics throw "64-bit GDS atomics are not implemented" (no test uses them)
- <a id="metal-b3-stage-lds"></a>LDS outside compute programs (function LDS of vertex/TCS stages) throws, naming B6
- <a id="metal-b3-store-order"></a>Stores of several lanes to one address: RDNA keeps the highest lane's data, Apple GPUs an unspecified lane's. Stores whose address operands are wave-uniform store from the highest active lane only. Per-lane addresses that happen to coincide keep an unspecified lane's data
- <a id="metal-b3-permute"></a>`ds_permute_b32` runs 32 shuffles per lane (a uniform loop over source lanes); `ds_bpermute`, swizzles, DPP and readlane are one or two shuffles (two per read for wave64 at two lanes per invocation)

### MetalBackend stage interfaces (macOS)

Gaps of the MSL vertex and fragment functions ([MslStageIo.cpp](../../core/shader/recompiler/MetalBackend/src/MslStageIo.cpp), [MslEntryPoint.cpp](../../core/shader/recompiler/MetalBackend/src/MslEntryPoint.cpp); work package B6, interface in [M2_DESIGN.md](../mac/M2_DESIGN.md) "B6/D6 interface"). Checked on the CPU by `agc_metal_msl_stage_io`.

- <a id="metal-b6-stages"></a>Only vertex (VS) and pixel programs: local/export, hull, domain, mesh and geometry-emulation stages throw naming B6; tessellation follows D-M2-1 (Metal 3 side queue)
- <a id="metal-b6-half-wave"></a>Wave64 vertex/pixel programs run at one lane per invocation, and Apple's SIMD groups are 32 wide (the emitter uses 32 even when a target claims 64): each SIMD group acts as a 32-lane view of the guest wave (ballots in the low word, votes over the group). `v_readlane` of a constant lane 32-63 throws unless it is the read of a matched half-wave reduction scan or the value is provably 0 there (as on the SPIR-V path for 32-lane hosts); a run-time lane (waterfall loops over EXEC) shuffles within the SIMD group and reads 0 past lane 31. Bit counts of whole-wave masks see one half only. B1's two-lanes-per-invocation mode (laneCount 2) cannot serve vertex or fragment functions: an invocation produces exactly one vertex or fragment, so it cannot run two guest lanes; a real wave64 graphics view needs mesh functions (threadgroups of 64). Vertex functions have no `[[thread_index_in_simdgroup]]`, so the lane id is `simd_prefix_exclusive_sum(1)`, which is the hardware lane only while the group is full MSL requests are laid out for 32 lanes whatever host width the target claims (Recompiler.cpp `HostSubgroupSize`; only `APS5_SINGLE_LANE` lays a program out for 64). The MSL corpus (`agc_metal_msl_corpus`) reports two recompiler test shaders recorded for a 64-lane host ([ShaderMemory.cpp](../../core/libs/prx/libSceAgcDriver/tests/ShaderMemory.cpp) `v_readlane_b32` of lane 63 in wave64 pixel programs) as host-width-rejected: SpirvBackend refuses them on 32-lane hosts too. Running them needs a 64-lane graphics wave: vertex programs as mesh functions (the D23 machinery, threadgroups of 64), or a phantom upper half (two lanes per invocation with lanes 32-63 inactive from entry, a legal partial wave whose lanes only whole-wave-mode code writes).
- <a id="metal-b6-per-vertex"></a>Per-vertex pixel inputs (`GetInterpolationParameter*`, barycentric-mode interpolation) read the triangle-vertices corner values `pv<L>_<corner>` and the emulated weights `aps5_bw`/`aps5_bwl` ([Metal skips](#metal-per-vertex-values)); the 16-bit delta rounds to half with MSL's float-to-half conversion (round to nearest even, as SPIR-V's OpFConvert under RTE)
- <a id="metal-b6-rect-flat"></a>Rect lists expand in the vertex function (6 host vertices, 3 guest vertex invocations each). The vertex function cannot see which parameters the fragment reads flat, so the fourth corner interpolates every parameter, and Metal's flat shading takes each triangle's first vertex RunRectangle of agc_driver_provoking_vertex is not run (upstream f2a4236ab last-vertex rect lists; see metal-rect-list-last-vertex).
- <a id="metal-b6-multi-location"></a>A pixel input interpolated at more than one of center, centroid and sample (its I/J pairs enabled for several locations in SPI_PS_INPUT_ENA) throws "interpolates pixel input N at more than one of center, centroid and sample" (MslStageIo.cpp): a Metal fragment input carries one qualifier. Needs `interpolant<T, interpolation::...>` inputs with `interpolate_at_center/centroid/sample` (MSL 2.3+). Seen in ASTRO BOT (PPSA21564), pixel shader 0x500418200, input 0
- <a id="metal-b6-gaps"></a>Not yet: stencil export capability checks. (`PackedAncillary` arrives composed from `RasterPrimitive` and `SampleId` by the front end since upstream #4031.)
- <a id="metal-cull-distances"></a>Guest cull distances (`PA_CL_VS_OUT_CNTL`, upstream #423) have no Metal output: the vertex function records each guest vertex's distances and writes one more clip distance per primitive, -1 at every vertex when all the primitive's vertices are negative on one plane (MslAbi Version 10, [MslEntryPoint.cpp](../../core/shader/recompiler/MetalBackend/src/MslEntryPoint.cpp)). That needs every vertex of the primitive in one invocation: triangles draw as triangle-vertices draws (three guest vertex runs per host vertex, as [metal-per-vertex-values](#metal-per-vertex-values)), rect lists use their three guest vertices (the derived fourth corner is not consulted), points use `APS5_CULL_POINTS`; lines and domain programs with cull distances throw; mesh (NGG) programs cull in the mesh function ([metal-mesh-cull-distance](#metal-mesh-cull-distance)). NaN is not negative (the console's choice is not measured). The emulated distance takes a clip distance, so guest clip distances plus the all-zero position distance plus the cull verdict must fit Metal's 8.
- <a id="metal-single-lane"></a>Vertex and local programs on a target without `vertexSubgroups` (upstream #4470; the Metal target follows the profile's vertex SIMD-group self-test) are laid out as one-lane waves; the library maps the MSL SIMD-group functions to one-lane values with macros ([MslEmitter.cpp](../../core/shader/recompiler/MetalBackend/src/MslEmitter.cpp) `SingleLaneDefines`). Only compiled (`agc_metal_msl_upstream_parity`), never drawn on this Mac, whose vertex SIMD groups pass the self-test.
- <a id="metal-early-depth-export"></a>Pixel functions whose request sets `earlyZ` (DB_SHADER_CONTROL `DEPTH_BEFORE_SHADER`, upstream #4210) get `[[early_fragment_tests]]` unless they use alpha-to-coverage, as on the SPIR-V path, and also unless they export depth or a stencil reference: Metal refuses the attribute on a function that returns `[[depth]]` or `[[stencil]]` (MSL specification 5.1.2), where Vulkan runs the tests early and ignores the exported values. Such shaders test late on Metal ([MslStageIo.cpp](../../core/shader/recompiler/MetalBackend/src/MslStageIo.cpp)); dropping the export instead is not implemented. The console's behaviour for that combination is not measured upstream either.
- <a id="metal-ancillary-layer"></a>The ancillary word's render target index (upstream #5097) reads `[[render_target_array_index]]` in every pixel function that reads the field and multiplies it by the `LayerExported` function constant; a vertex, mesh or domain function that writes no layer still links with it (`agc_metal_msl_upstream_parity`), and its value is then discarded. What Metal returns for an unwritten layer is not relied on.
- <a id="metal-gds-coherent"></a>GDS plain `ds_read` / `ds_write` (upstream #4279, the Coherent gds buffer) are relaxed atomic loads and stores on Metal ([MslMemory.cpp](../../core/shader/recompiler/MetalBackend/src/MslMemory.cpp)), like GLC buffer reads, since a plain device load may hit a stale cache line; the cost on GDS-heavy shaders is not measured.
- <a id="metal-b6-function-lds"></a>LDS in vertex and pixel programs is per invocation (a thread array of `functionLdsDwords`, up to 8192 dwords when the front end cannot bound the addresses), as the SPIR-V path's Function-storage LDS; the large case spills to stack memory and is slow. No device arena is used for graphics stages
- <a id="metal-b6-raster-order"></a>Primitive-ordered pixel shaders bracket the whole guest program with a read and a write-back of one dword (by pixel position) of a `[[raster_order_group(0)]]` buffer (MslAbi::BufferIndex::RasterOrder). Metal documents ordering for accesses to the group's resources; the guest's accesses through address-made pointers stay between the two because the compiler cannot prove them apart, which is an assumption about the compiler, checked only by `agc_driver_pixel_interlock`

### Metal recorder and buffer primitives (macOS)

Gaps of the Metal twins of the recorder and the buffer primitives ([Recorder.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/Recorder.mm), [MetalCommandStream.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/MetalCommandStream.mm), [Resources.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/Resources.mm), [BufferPool.mm](../../core/libs/prx/libSceAgcDriver/specifics/macos/src/BufferPool.mm); work package D2 in [M2_DESIGN.md](../mac/M2_DESIGN.md)). Unsupported states throw `Metal recorder (work package D2): ...`.

- <a id="metal-d2-device-integration"></a>Not wired into the device yet: the Metal device (D1) records its dispatches into command buffers of its own and has no recorder, so the label table, pending-write snapshot, completion actions and GPU label stores of the recorder are unused until `MetalDevice.mm` creates one (recipe in M2_DESIGN §9 D2)
- <a id="metal-d2-barriers"></a>Bring-up barrier policy: every encoder starts with a consumer queue barrier over all earlier stages, so batches and encoders never overlap on the GPU; dependent commands inside a compute encoder rely on their recorded barriers. M4 replaces this with precise barriers from the guest's flush and acquire packets
- <a id="metal-d2-render-barriers"></a>A pipeline barrier recorded inside a render pass ends the pass (Apple GPUs have no intra-pass barrier that waits for fragment work); the draws of D6 must not record one where a pass break changes load/store behaviour
- <a id="metal-d2-occlusion"></a>Occlusion samples are counted only through the fold kernels (segment mode): a render pass after `PrepareSampleSlot` must name `Recorder::SampleVisibilityBuffer()` as its visibility result buffer with `MTLVisibilityResultTypeAccumulate` (D6), and a process whose fold kernels fail to build cannot count samples (`beginSamples` throws) instead of falling back to whole-batch queries
- <a id="metal-d2-feedback"></a>A GPU failure reported by commit feedback can surface one finish late: the feedback handler runs after the batch's event value on macOS 27.0.1, so the failure is raised by the next batch that finishes
- <a id="metal-d2-hang"></a>A batch still running after `APS5_METAL_BATCH_TIMEOUT_MS` (20 s) fails the wait with a thrown error and its command buffer, allocator and upload memory are leaked (no device-lost recovery); the upstream recorder waits forever, reporting every 5 s
- <a id="metal-gpu-timing-render-ranges"></a>GPU timing (`APS5_PROFILE_GPU`) of ranges inside render passes: the per-range stamps around draws come back unwritten (MTLCounterErrorValue) on this TBDR GPU, so `[gputime]` leaves them out and counts them (D59; ~450 per 10 s on Showcase 1.0.2) and draw time shows up only as "untimed" batch time. Per-draw GPU time needs stamps at render pass stage boundaries (`MTL4TimestampGranularityRelaxed` / pass begin and end) or a pass per timed range in a profiling mode. `timingPresents` is never counted on Metal (the line says 0 presents).
- <a id="metal-d2-render-target"></a>`RenderTarget` (Resources.hpp) throws: it needs D4's Metal format table and D6's render passes
- <a id="metal-d2-mock-tests"></a>Vulkan-mock tests: `agc_recorder_kept_bytes` and `agc_buffer_pool` run Metal twins of their checks (`specifics/macos/tests/*Metal.mm`, swapped in by `twins/D2-recorder.cmake`); `agc_driver_graphics` (tests/Graphics.cpp, MockVulkan) runs through T1's twin: its descriptor pool and cache checks as Metal twins, without its cases that build a `Buffer`, `BufferPool` or `Recorder` on a mock Vulkan context ([Metal skips](#metal-vulkan-internal-tests))
