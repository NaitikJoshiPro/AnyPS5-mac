# Decisions

One entry per decision. Newest at the bottom. Format: context, options, evidence, choice, date.

## D1: Fork, not upstream (2026-10-12)
Upstream accepts macOS only as x86-64 + MoltenVK with unchanged rendering (issue #1). Our goals (arm64, Metal, reworked rendering) conflict, so we work on branch `mac-native` and push nothing without the user's approval.

## D2: No Rosetta in the product path (2026-10-12, user decision)
The game process is arm64 only. Reasons: the user wants native performance; Apple ends Rosetta support after macOS 27. Rosetta as a *test-only* oracle for the CPU translator is still an open question for the user (MISSION §6.4).

## D3: Metal, not MoltenVK (2026-10-12, user decision)
Rewrite the GPU path: new `MetalBackend` in the shader recompiler and a Metal driver in libSceAgcDriver, designed for TBDR. Keep the recompiler front end (decoder, control flow, translation, IR, optimization) because it encodes measured RDNA2 behaviour. MoltenVK failure list in MISSION §5 is the requirements list.

## D4: Generic binary translation, no per-game reverse engineering (2026-10-12, user decision)
The CPU layer is a game-agnostic x86-64 → ARM64 translator: AOT from executable metadata (`.eh_frame`, relocations, NID tables) plus a JIT fallback with a persistent cache. Open sub-decision for M1: LLVM AOT backend vs a direct emitter, and whether to borrow from FEX (MIT ≤ `ac555dd8`). Decide with measurements.

## D5: Storage budget 100 GB (2026-10-12, user decision)
Everything the port creates stays ≤ 100 GB; `tools/mac/disk_budget.sh` enforces it. Only storage exceptions require asking the user.

## D6: FEXCore is the M1 translator engine; our own AOT discovery and per-title cache on top (2026-10-12)
Context: D4 left open LLVM AOT vs a direct emitter vs borrowing FEX. arvindfroi's runner `aps5-fex` (mugurc/AnyPS5#4, merged here) already runs guest programs through FEXCore in-process.
Options and evidence (`.mac-work/research/translator-perf.md`, `runner-arch.md`):
- (a) FEXCore JIT + our AOT discovery (`.eh_frame`, relocations, exports, init arrays) + persistent cache: est. 0.7–0.9× native on integer loops, 0.6–0.9× SSE, 0.4–0.7× AVX2 (no SVE on M3: upper YMM halves live in memory); 2–4 agent-days.
- (b) LLVM lifter + JIT fallback: published lifters run 1.5–4.8× slower than native (Lasagne, Instrew, Elevator); yabanana's #1553 covers 3 scalar functions and relies on per-game annotations (forbidden by MISSION §1). 3–6+ agent-weeks, and still needs a JIT.
- (c) Own emitter: months to reach FEX's coverage (AVX2, x87 80-bit via SoftFloat, TSO modes).
- Measured on this M3 (cycles/op, `.mac-work/research/tsobench/`): LDAPR/LDAPUR 0.60 vs LDR 0.35; STLR 1.0 vs STR 0.5; ordered vector accesses 11–21×. Taken under heavy load: ratios valid, absolute ns not.
Licence: arvindfroi/FEX `cad0c096` audited (`.mac-work/research/fex-licence.md`): FEX-2607 + 55 willfaust commits ending at `ac555dd8` (MIT) + 15 FEX-Emu backports (MIT, byte-identical to upstream) + 6 arvind commits; no willfaust commit after `ac555dd8` (his GPL-3 switch is `188e8224`, 2026-08-28). Nested deps: fmt (MIT), xxHash lib (BSD-2), range-v3 (BSL-1.0), unordered_dense (MIT), cephes (BSD), SoftFloat-3e (BSD-3). All GPL-2.0-compatible.
Choice: (a). Pin `3rdparty/FEX` at `cad0c096` (no `branch =` drift), guard it with a licence test, keep a git bundle backup in `.mac-work/ref/`, take future FEX fixes only from FEX-Emu (MIT), never from willfaust after `ac555dd8`. Keep FEX patches local (FEX-Emu's CONTRIBUTING forbids AI-generated contributions, and we push nothing without the user). Revisit only if M1 microbenchmarks stay below 0.7× native on integer/SIMD loops after tuning; LLVM stays an option for measured hot functions in M4.

## D7: CPU translator test oracle: FEX's x86 ASM unit tests, no Rosetta (2026-10-12)
Context: MISSION §6.4 (no x86 hardware here). FEX ships ~2,222 nasm unit tests whose expected register/memory values are checked on real x86 hardware in FEX's CI (MIT). Choice: port them to run under `aps5-fex` as the per-instruction oracle, plus SDM-derived expectations for anything they miss. Rosetta is not needed as an oracle, so the user question in §6.4 is moot. 1,020 tests use scratch addresses below 4 GiB, which macOS arm64 can't map: the harness moves 1,007 of them up by `0x10_0000_0000`; 13 can't be moved (recorded skips). All 2,222 assemble with nasm 3.02.

## D8: M2 shape: MetalBackend from IR + the VulkanDevice API implemented on Metal (2026-10-12)
Evidence (`.mac-work/research/m2-scope.md`): the IR (SSA, 469 opcodes, structured if/loop markers) has almost no SPIR-V dependency; SpirvBackend has one call site (`Recompiler.cpp:427-436`). The driver has no abstraction layer, but only 23 files (~27.4k lines) call Vulkan, and ~329 of the 336 `agc_driver_*` tests use only the public `VulkanDevice` API. Upstream notes the suite already passes under MoltenVK on Apple GPUs except 16 hardware-limit tests.
Choice: `MetalBackend` emits MSL at the SpirvBackend call site (SpirvBackend keeps compiling for differential tests). The `VulkanDevice` API is implemented on Metal in Objective-C++ under `libSceAgcDriver/specifics/macos`, swapped in by CMake on Apple with an overlay include directory, so upstream files stay untouched except CMake. Vulkan-Headers stays as header-only enum/struct types; nothing loads or calls Vulkan. SPIRV-Cross (core files dual "Apache-2.0 OR MIT", used under MIT) may be used in dev builds only, as a bridge and differential oracle, never shipped. Rejected: a Vulkan-on-Metal layer (violates D3), a new abstraction layer (rewrites a Vulkan path we can't test here), a clean-slate driver (loses behaviour the tests check). Metal 3 vs Metal 4 command API: decided in `docs/mac/M2_DESIGN.md`.

## D9: Two parallel build streams; milestones still close in order (2026-10-12)
Context: CLAUDE.md allows at most two live build directories; the M3 Air has 8 cores. The CPU stream (M0 → M1 → M3 integration) and the GPU stream (M2) share almost no files. Choice: main worktree + `build-arm64` for M0/M1; a git worktree `.mac-work/wt/metal` (branch `mac-native-metal`) + `build-metal` for M2; agents sharing a build directory serialise ninja/ctest with `tools/mac/buildlock.py`. Prep work that needs no build (tools, design, title preparation) runs in build-less worktrees. Each milestone is still closed in order with its exit criteria verified.

## D10: No hardware TSO; emulate x86 ordering with LRCPC (2026-10-12)
Evidence: the TSO enable bit is set only by the kernel (Rosetta); no API, entitlement or sysctl in the macOS 27 SDK exposes it, and the TSOEnabler kext needs SIP off. Hypervisor.framework lets a VM vCPU enable TSO (probed here with an ad-hoc-signed binary: worked; one VM exit ≥3 µs), which is too slow for a game process calling native libraries constantly. Choice: FEX's default ordering (integer loads/stores LDAPR/STLR, vector ordering off, stack accesses unordered); further elision (frame-pointer locals, TLS, read-only data) only with measurements in M4.

## D13: Vendor FEX at FEX-Emu FEX-2610 plus our macOS series (supersedes D6's pin) (2026-10-12)
Context: M1 needs JIT results persisted and reused. Evidence (`docs/mac/M1_DESIGN.md` "Code cache: verdict", file:line checked): the pinned FEX's FXCC cache is off by default (`EnableCodeCachingWIP=false`), has never worked on macOS (`CodeCache.cpp:607-612`), is invalidated by every FEX rebuild, never checks guest bytes, and needs a Linux-side generator; the `.eh_frame` AOT generator is never called. FEX-2610's DiskCache lives entirely in FEXCore, caches ordinary JIT output, checks guest bytes on every hit, is address-independent, capped at 1 GiB and uses `flock`. A trial rebase of the macOS delta (61 commits after dropping the 15 backports already upstream) stopped 14 times with 45 hunks (30 in code we build; the code-buffer cluster onto upstream's `SharedCodeBufferManager` is the hard part). Staying on the pin would mean 400–700 runner lines on the broken FXCC path; the rebase is ~3 agent-days but also brings ~3 months of upstream fixes.
Options for hosting the rebased FEX: (1) a fork on GitHub (needs a push, i.e. the user's approval); (2) FEX-Emu as the submodule plus patch files applied at configure time (pristine upstream, but every FEX edit during active development must be re-exported); (3) vendor it in our repo.
Choice: (3). `git subtree add --squash` FEX-Emu `FEX-2610` at `3rdparty/FEX`, then apply the slim macOS series (willfaust ≤ `ac555dd8` + arvind's, dropping Windows/iOS-only commits) with `git am --directory=3rdparty/FEX`, preserving authorship; FEX's own `External/` dependencies become submodules of our repo. Updates come with `git subtree pull --squash` from FEX-Emu only. The licence guard (`tools/mac/check_fex_licence.py`) checks the recorded upstream base and scans for GPL-3 markers. No push is needed, so the user question in M1_DESIGN R is moot. Keep the git bundle of `cad0c096` until M1 closes.

## D15: Build and test conventions for the arm64 fork (2026-10-12)
- The full macOS build defaults to arm64 (top-level CMakeLists.txt); x86_64 stays selectable with `-DCMAKE_OSX_ARCHITECTURES=x86_64`. Reason: this fork's product is arm64-only (D2).
- GPU tests carry an explicit per-test `gpu` label (468 tests in libSceAgcDriver, libSceAgc, libSceVideoOut): `ctest -LE gpu` is the non-GPU suite; `-L gpu` is run one at a time with timeouts only (GPU safety). A directory `LABELS` property is not enough: CTest ignored it for tests that set `WORKING_DIRECTORY`.
- `no_x86_build_path` (the M0 "no x86 on the arm64 path" proof, ~12 min on all cores) carries the `slow` label: routine runs use `-LE "gpu|slow"`, milestone ends run it.
- Guest-state operations (getcontext/setcontext/makecontext/swapcontext, sigsetjmp/siglongjmp, the sceKernelRaiseException register snapshot) on arm64 go through runner hooks; without a runner they validate arguments and throw a `std::runtime_error` naming the function, and their tests skip with that reason (M1 package G wires them).
- Agents sharing one worktree commit only named paths (`git commit -- <paths>`), because the index is shared.

## D16: M2 architecture (Metal 4 driver, MslAbi, twins, caching) (2026-10-12)
Full text with evidence: `docs/mac/M2_DESIGN.md` §1 (on `mac-native-metal`). Summary:
- **Metal 4 command model** for every queue the driver records on; one `MTL4CommandQueue` + one `MTL4Compiler` per device (a process holding >100 Metal 4 queues panicked an M3 Max on 27.0.1). Probe on this M3: both APIs ~1.0–1.3 µs CPU per dispatch; Metal 4 without barriers overlaps 1000 dispatches (2 ms vs 5–8 ms); it maps 1:1 onto upstream's Vulkan-shaped recorder (stage-mask barriers, allocators, untracked resources, address bindings, shared events); Mesa KosmicKrisp is Vulkan 1.4 conformant on the M3 using Metal 4 only. Gap: no tessellation in `MTL4RenderCommandEncoder` → skip first, then a Metal 3 side queue with event hand-off, mesh-shader tessellation in M4. Presentation via Metal 4 with a Metal 3 fallback switch. Bring-up barriers are conservative; M4 relaxes them from guest acquire/flush packets.
- **MslAbi v1**: four fixed buffer slots per function (dense per-stage descriptor table as a Tier-2 argument buffer written by the CPU, 256 B push data, large-LDS arena, driver-data record); specialization constants → function constants; each shader reports its layout (`MslAbi::Reflection`) and the driver binds by it. Changes are append-only with a version bump.
- **Twins**: the class keeps the name `VulkanDevice` (5 `make_shared<VulkanDevice>` call sites); Metal versions of upstream driver files live under `specifics/macos` with overlay headers searched first and per-package swap lists; transitional Vulkan handle types may carry Metal objects until every user is twinned. M2-end check: no Vulkan-calling original left in the Apple build (`nm -u … | grep ' _vk'` empty).
- **Guest memory** wrapped in place per allocation (`newBufferWithBytesNoCopy`, shared, untracked, one residency set), never the whole arena, never PROT_NONE/executable pages (mirrored by copy with write-back instead).
- **Shaders**: MSL text from the IR with prelude chunks owned by instruction families; `ulong` native, f64 in software, every IR value function-scope, every loop bounded by a runtime guard that records a `LoopLimit` fault (also protects the GPU from runaway guest loops). Compile with `MTL4Compiler` on background threads at shader registration; pipelines persist in a per-title `MTL4Archive` (binaries-only serializer; binaries+descriptors fails on 27.0.1), `MTLBinaryArchive` fallback; "second run compiles 0 pipelines" = archive lookups that cannot compile.
- **No SPIRV-Cross on the critical path** (MetalBackend already runs real tests; hardware-measured expected values are the oracle).
- **Skips** only for documented Apple hardware limits, via `tools/mac/m2_skip_allowlist.txt` + `check_skips.py --job macos`; f64 and 64-bit atomics are emulated, not skipped.
Foundation result: `agc_driver_vop1_control` passes end to end on the GPU via MetalBackend; G1 baseline 29/196 compute tests pass, 29 skip, 138 fail, 0 hangs.

## D18: Runner defaults: strict split locks, opt-in disk cache (2026-10-12)
- FEX's `StrictInProcessSplitLocks` is on by default: unaligned locked accesses that cross 16 bytes are otherwise emulated with two CASes and tear (measured: 11 of 12 wrong counts across 4 concurrent copies without it, 12/12 correct with it).
- The JIT disk cache (FEX-2610 DiskCache, content-checked) is enabled when `APS5_FEX_CACHE_DIR` is set or a directory above the executable is named after a title ID; `aps5-fex --precompile` seeds it ahead of time from `.eh_frame` FDEs, exports, relocation targets, init/fini arrays and the entry point.

## D19: GPU safety rules after the 2026-10-12 kernel panic (user-approved 2026-10-12)
Evidence: `.mac-work/feedback/gpu-safety-proposal.md` (panic during process teardown of a test using an untested, half-edited Metal 4 device; one residency set never removed from the queue). The user lifted the GPU freeze ("all gpu tests are allowed now") on these terms:
1. GPU tests run only through `tools/mac/gpu_suite.py` (or a ctest call wrapped by it), which refuses when the build that produced the binaries has uncommitted changes under `core/`, when any GPU test binary or the prx is stale vs its inputs, when the 1-minute load average is > 6, or when a compiler/linker is running. Record prx hash + HEAD per run.
2. Canaries first in every session (3 known-good tests); stop on any failure.
3. A shader corpus that doesn't compile (offline `xcrun metal` once installed, else `agc_metal_msl_compile`) means its tests are not launched.
4. Validation (`MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1`) for new shader families, device/recorder/residency/teardown changes and quarantined-test reruns.
5. Driver teardown hygiene: every residency set removed from the queue, wait for the last submitted value before releasing, drop `__DATA` wrappers, join the release thread.
6. One test per process, timeout ≤30 s, 2 s pause between tests. Quarantine list fails closed.

## D20: Per-vertex fragment values are emulated through triangle-vertices draws (2026-10-13)
Context: user order (2026-10-13 ~05:50) "no Apple limits, only things still to emulate". RDNA pixel shaders read per-vertex attribute values (`v_interp_mov` P0/P10/P20, `v_interp_p1ll/p1lv/p2_f16`, exact I/J); Vulkan has them through VK_KHR_fragment_shader_barycentric, upstream emulates them with a generated geometry shader otherwise. Metal's per-vertex fragment values (`vertex_value<T>`) are Apple10-only (Metal Feature Set Tables, 2026-05-21, https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf), and Metal has no geometry stage. `[[barycentric_coord]]` is Apple7+ but documents no relation to a vertex order the shader could index.
Options: (a) mirror upstream's geometry-shader emulation in the vertex function: a non-indexed draw with 3 host vertices per guest triangle, each running the guest vertex program for its triangle's 3 guest vertices and emitting the corner values as flat outputs plus one-hot corner weights as interpolated barycentrics; (b) a compute pre-pass writing the vertex outputs to a buffer, the fragment function reading them by `[[primitive_id]]` (needs a second pass, an output buffer sized per draw, and primitive_id ordering that matches the index expansion); (c) mesh shaders (object/mesh functions emitting the triangle with per-primitive data).
Choice: (a). It reuses the rect-list expansion already in the emitter, shares its driver plumbing with DRAW's conservative-rasterization emulation (one contract, MslAbi Version 5: `BufferIndex::TriangleVertices`, `TriangleVerticesHeader`, macros `APS5_TRIANGLE_VERTICES`, `APS5_PER_VERTEX_LOCATIONS(_HI)`, `APS5_BARYCENTRICS`, `APS5_CONSERVATIVE`), and its corner order is the one the driver writes, so P0/P1/P2 and the weights agree by construction (no reliance on `[[barycentric_coord]]` ordering). The Metal target advertises `fragmentShaderBarycentricEnabled`; on the MSL backend the recompiler still translates with host interpolation first and re-translates with barycentrics only the programs that need them (16-bit interpolation now marks the program instead of throwing), so ordinary draws keep indexed drawing. Costs (3x vertex invocations, 3x varyings per per-vertex location, centre-only I/J) are in TechnicalDebt `metal-per-vertex-values`; M4 may use native `[[barycentric_coord]]` for I/J-only programs once its order is measured.

## D21: Conservative rasterization is emulated in the triangle-vertices mode (2026-10-13)
Context: user order (2026-10-13 ~05:50) "no Apple limits, only things still to emulate". The Metal API has no conservative rasterization (no property in the macOS 27.0 SDK headers, MTLRenderPipelineDescriptor included), and the Metal Feature Set Tables (https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) list none for Apple9 or Apple10; the allowlisted skip (`has no VK_EXT_conservative_rasterization`) was temporary.
Options: (a) GPU Gems 2 ch. 42 (https://developer.nvidia.com/gpugems/gpugems2/part-v-image-oriented-computing/chapter-42-conservative-rasterization) in the vertex function, which needs the whole triangle per host vertex: the D20 triangle-vertices mode already provides it; (b) a compute pre-pass writing grown triangles to a buffer, then a normal draw (an extra pass and a per-draw buffer); (c) mesh functions emitting the grown triangle (needs the MSL mesh stage, not ready).
Choice: (a), sharing D20's contract (MslAbi v5, `APS5_CONSERVATIVE` = 1 overestimate / 2 underestimate): DRAW 9ec6a7ffb (driver), 07fe3aac8 and a8aa31286 (MslConservative.hpp text hooks), SHD3 3f14bf8ad/639a3d393 (emitter calls the hooks). Vertex: each corner moves to the intersection of its two edges' offset lines (half-pixel projection on the edge normals, bounded for sharp corners). Fragment: exact separating-axis test (x, y, three edge normals) of the pixel square against the triangle, discarding misses; degenerate triangles become their vertices' box grown by half a pixel. `VulkanDevice::ConservativeRasterization()` is true on Metal.
Evidence: `agc_driver_conservative_rasterization` (off, overestimate incl. a sub-pixel and a degenerate triangle, off again) passes under --validation (gpu-suite/shd4-conservative, HEAD d80f1643a); its m2_skip_allowlist entry is removed. Costs and gaps: TechnicalDebt `metal-conservative-rasterization` (3x vertex work, triangles only, fixed half-pixel overestimation size). M4 may move both D20 and D21 to mesh functions to restore post-transform reuse.

## D22: Multisampled storage images are emulated as 2D arrays of layers * samples slices (2026-10-13)
Context: user order (2026-10-13 ~05:50) "no Apple limits, only things still to emulate". Four G4 tests (`agc_driver_prepared_shaders`, `_debug`, `_indirect`, `_uncached`) failed in MSL emission with "stores to a multisampled image, which Metal shaders cannot write" (gpu-suite/shd3-v2-upstream). MSL multisampled textures (`texture2d_ms`, `texture2d_ms_array`) support only `access::read` (Metal Shading Language Specification, section 2.9 Textures: https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf), and no Metal GPU family offers shader writes or atomics on them (Metal Feature Set Tables: https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf). Upstream fact (GuestTextureResource.cpp `resolveDimension`): guest T# types 14/15 (MSAA) are rejected on every platform, so today only placeholders reach these heaps at run time.
Options: (a) storage heaps of the MSAA dimensions become `texture2d_array` with slice = layer * samples + sample, the sample count a function constant; (b) a buffer backing with computed addresses (loses texture formats and texture atomics); (c) alias a 2D-array view or heap alias over the multisampled texture: rejected, a 2DMultisample texture can only be viewed as a multisampled type (newTextureViewWithPixelFormat:textureType: compatibility; Dawn forbids the same view for this reason: https://dawn.googlesource.com/dawn/+/10ec4ee7efb3c0fd10bdb7191da77cdd6d063ea9), and Apple documents no sample layout for heap aliasing.
Choice: (a), MslAbi v6 (MSIMG). Emitter: stores, 32-bit atomics and 64-bit lock-table atomics address slice l * n + s, bounds x/y, s < n and l < slices / n; n = `PipelineSpecialization::SampleCountBase` (12288) + resource for direct images (the binding plan supplies 1 << T# LAST_LEVEL), the T# metadata for table images. The MSL target needs `CapabilityStorageImageMultisample` as SPIR-V does. Binding plan: `Image2DArray` shape on MSL. Placeholders: single-sample 2D arrays. The run-time coherence design for real guest MSAA images (shadow 2D array, compute copy MS to shadow, per-sample render pass shadow to MS, dirty tracking) is recorded in TechnicalDebt `metal-ms-storage` until guest MSAA T#s are decoded.
Evidence: `agc_metal_msl_ms_storage` (new): MSL shape of 6 programs on the CPU, Metal compile, and dispatches of the store and 32-bit atomic programs on 8x8 backings of 2 layers * 4 samples writing exactly the addressed sample's slice (gpu-suite/msimg-t7, --validation). G4 results in PROGRESS.

## D31: Guest mappings in the macOS GPU carveout are displaced to an alias at guest | 1<<40 (2026-10-13)

## D33: The displaced window is a table of host-reserved ranges: shared region tail, commpage guard, GPU carveout (2026-10-13)
Context: SuperTuxKart's Mesa winsys advertises a GPU VA high range of 0x4_0000_0000-0x24_0000_0000 with CPU and GPU at one address (oops-mesa `src/winsys/device_info.c:56-63`); radeonsi's first GEM_VA batch-maps at fixed 0x400000000 and failed with "fixed guest mapping overlaps a host region in the guest arena". 0x400000000 is inside the dyld shared region.
Measured (`.mac-work/scratch/va2/probe2.c`, `hdr.c`, macOS 27.0.1, this boot): `__shared_region_check_np` = 0x18A850000; the cache header gives sharedRegionStart 0x180000000, sharedRegionSize 0x1B9B14000, maxSlide 0x20000000, slide 0xA850000. Descending into the shared-region submaps with `mach_vm_region_recurse`, the last accessible entry ends at 0x344364000 (so LIBS2's "tail from 0x2E0000000" was wrong: 0x2E0000000-0x2E0760000 is a prot-0 gap and the cache's last subcache runs on to 0x344364000); [0x344364000, 0xFC0000000) is one prot 0/0 entry of the submap, and reads at 0x400000000, 0x8000004EA and 0xF00000000 raise SIGBUS. Worst case over slides: the cache ends below 0x180000000 + 0x1B9B14000 + 0x20000000 = 0x359B14000 (~13.4 GiB), so 0x400000000 is always in the tail on this macOS. The commpage guard [0xFC0000000, 0x1000000000) is a prot-0 `VM_MEMORY_GUARD`; it abuts the carveout.
Options: (a) take the tail over with `mach_vm_allocate(VM_FLAGS_OVERWRITE)` (works today): rejected by main; it is undocumented, replaces part of the shared-region submap, and depends on dyld and xnu behaviour that can change with any update. (b) Generalise D31: displace every guest range the host has reserved or cannot safely own.
Choice: (b). `GuestDisplaced.cpp` builds a table at startup (`GuestDisplacedRanges_nid_no_patch`): the GPU carveout (required, checked to be inaccessible end to end); the commpage guard (when inaccessible); the shared region tail, from the end of the last accessible leaf at or above the shared cache (`__shared_region_check_np`) to 0xFC0000000, accepted only when every leaf in it is a prot-0/max-prot-0 submap entry with no hole, and cross-checked against the cache header's extent plus slide. If the lower ranges' alias cannot be reserved they are dropped and the window falls back to D31's carveout; `APS5_DISPLACED_CARVEOUT_ONLY=1` forces that. The JIT stub's range check now loads the window start and size from two literals in the stub (`ldr, sub, ldr, sub, bic, tbz #63`: the same 6 instructions as D31's shift test, no NZCV). `IsDisplaced`/`HostAddress` do a constant coarse compare against [0x180000000, 0x7000000000) first and only then call `GuestDisplacedStart_nid_no_patch()` (a function: the patched libraries export functions, not data); fex, which does not link libc, uses the coarse test only (the shared cache below the window is never guest memory). The arena never first-fits into the window (it stays one used range); fixed guest mappings inside it are tracked apart. The fault handler, JIT backpatching, `GuestArena::HostAddress`, DirectMemory, write watch, the AGC `GuestMemory` primitives and the Metal import all go through the same window, unchanged.
Straddles: the ranges inside the window share one contiguous alias, so a range may cross between them; across the window's lower edge (the end of the shared cache) or 0x7000000000 the arena throws "straddles the edge of the displaced window". The PS5 system-reserved range 0x7FFFFC000-0x1000000000 (which covers the tail/commpage and commpage/carveout boundaries) stays refused for fixed guest mappings, as on every host, now with its own message ("overlaps the PS5 system-reserved range"); the console libkernel gadget at 0x8000004EA stays a FEX thunk (D32). Usable for guests: [end of cache, 0x7FFFFC000) (~18.9 GiB here, at least 18.6 GiB at any slide) and the carveout.
Measurements (`.mac-work/scratch/va2/bench`, FEX, 32 MiB store+load loop, best of 9, ticks): ordinary memory through unpatched sites 5.0-8.3 M; ordinary memory through sites already patched for a displaced address 27-62 M; displaced memory through patched stubs, carveout 24-43 M, tail 0x400000000 24-36 M. D31's check sequence measured the same within noise (unpatched 6.9-16 M, patched-ordinary 47-60 M, displaced 34-40 M), so the table costs nothing over D31. Correction to D31: its "0.99x of an ordinary mapping" compared displaced accesses with ordinary accesses through the same patched sites; against unpatched sites a displaced access in a tight loop costs ~4-6x, and an ordinary pointer through a patched site ~5-8x (the stub spills two registers, runs the check and takes two branches). Titles that never touch the window pay nothing (no site is patched); see TechnicalDebt for the cost to titles that do.

## D35: Displaced guest buffers reach the kernel through a host system call shim, not through bridge pointer translation (2026-10-14)
Context: D31/D33 back host-reserved guest ranges at `guest | 1<<40`. Native code that touches a displaced address is correct but slow (two signals per load/store). A host system call given one fails outright (EFAULT: the kernel copies in or out and raises no signal). VA3 translated about 60 native paths by hand (a9cabe02e, de5d3dad5, 2cd1c9e2d). Any other export that hands a guest buffer to the kernel still fails, and every future library would need the same audit. Question: can the guest→native boundary handle this generically?
Measured (build-metal, 2026-10-14, `.mac-work/logs/va4/`):
- Signature coverage: the generator (`core/fex/tools/gen_bridge_signatures.py`, libclang) gives 3722 signatures. Every guest-callable function is covered: 1217 of the 1352 `_nid_` exports, and the other 135 are data (`_nid_postfix` objects such as `__stdoutp`) or host-only helpers. 2352 signatures (63%) take at least one pointer (3698 pointer parameters: 1269 `void*`/`char*`, 1277 struct or opaque, 584 pointer to scalar, 326 pointer to pointer, 178 function or member types, 52 wide strings). 319 return a pointer.
- What the table cannot say: `BridgeKind::Pointer` has no pointee. `const iovec*`, `msghdr*` and every SDK info struct are opaque pointers. Record leaves (`BridgeLeafKind`) are only Integer/Float/Vector, so a pointer field of a by-value struct looks the same as an integer. Nothing says whether a pointer is a transient buffer, an identity (a key, a handle, something stored and handed back) or an out-parameter that receives a pointer. libclang knows the field types, so the generator could emit pointer leaves and pointee layouts. It cannot emit the role.
- Host imports: the 131 prx libraries import 422 distinct libSystem symbols. About 99 of them cross the kernel with a user pointer: 54 take buffers or out-structs (read/write/pread/pwrite and their v forms, recv/recvfrom/send/sendto, socket address and option calls, poll/select/kevent, ioctl, the stat family, sysctl, getentropy, nanosleep, mach_msg...), 19 take paths, 13 are stdio, and 13 are identity (mmap/munmap/mprotect/mlock/munlock, mach_vm_*, sys_icache_invalidate: DirectMemory and the arena already translate these by hand). The rest is userspace (math, strings, pthread, dispatch, malloc), where a displaced address only means slow, never EFAULT. read is imported by 9 libraries, fwrite by 19, fread by 11, open by 10, recvfrom by 2. This includes third-party code linked into them (ffmpeg in AvPlayer, FreeType in Font).
- Interposition probes (`.mac-work/scratch/va4/`): a `__DATA,__interpose` library linked at launch catches direct calls from a dylib dlopen'd later, but not libSystem's own internal calls (fread of 1 MiB went to read(2) uninterposed: 0 of 1). The same library dlopen'd interposes nothing. A static archive with a hidden `read` linked into a dylib replaces libSystem's binding for every object in that dylib, third-party objects included. At 0x4000000000 that read returned 4096 bytes through the alias, where the unshimmed copy returned EFAULT. Cost: 479.6 vs 471.0 ns per 1-byte read from /dev/zero (best of 5 × 1M, interleaved; the second round 493.4 vs 493.3), within noise of the system call.
- Option C, rechecked: the shared region is a fixed nested submap, `SHARED_REGION_BASE_ARM64` 0x180000000 + `SHARED_REGION_SIZE_ARM64` 0xE40000000 = 0xFC0000000 (`mach/shared_region.h`), whatever the cache size. The tail is inside it, so no allocation can land there without `VM_FLAGS_OVERWRITE` of dyld's submap, which D33 rejected and this study does not reopen. `_POSIX_SPAWN_RESLIDE` only moves the cache's slide. The commpage guard and the carveout are permanent entries (D31). No alternative exists on macOS 27.
Options:
(A) Bridge: on entry, replace pointer arguments that fall in the window with their alias. Cost: one compare per pointer (the precise start, not fex's coarse [0x180000000, 0x7000000000) test, because pointers into the shared cache below the window are real host addresses). Benefit: native code then touches the alias at full speed (no fault path), which (B) does not give. It breaks pointer identity, because the alias leaks back to the guest:
- returned pointers derived from arguments (memcpy/strcpy return dst; strchr/memchr/strstr; fgets): fixable by mapping returned alias pointers back, one compare;
- pointer-to-pointer out-parameters (strtol's endptr, iconv's in/out cursors, strtok_r's saveptr; 326 parameters): fixable only for the top level, by rescanning after the call;
- pointers stored and returned later through structs or other calls (equeue udata from sceKernelAddUserEvent coming back in a waited event, AvPlayer/Ngs2 buffer infos, fiber and thread info): the bridge never sees them. The guest then compares or keys an alias against guest pointers, and loops like `while (cur < end)` stop at once (the alias is 1 TiB higher);
- exports that key host state on the guest address (DirectMemory munmap/mprotect/query, the write watch, the Metal import, which VA3 deliberately gives the guest address): they would get the alias and fail their lookups;
- pointers nested in structs (iovec, msghdr, SDK descriptors): not described by the table. Translating them means copying each struct, because in-place rewrites race with other guest threads and hit const memory;
- callbacks (native→guest) would pass alias pointers into guest code: the same identity hazard in the other direction.
Making (A) safe needs a per-parameter role (transient buffer or identity) that no type carries. That is a hand audit again, only declarative, and native→native calls bypass the bridge anyway.
(B) Translate at the host system call waist: the libSystem functions the prx libraries import. Only these can fail outright. The kernel never retains or returns a buffer pointer in this class, so translation is semantically invisible. Exceptions to exclude or handle: aio (retained aiocb buffers), kevent udata (opaque, never translated), the identity group above, and fgets returning its buffer (map back). Cost: one compare per pointer argument plus an indirect call, below noise next to the system call. Mechanism: a static library with hidden definitions linked into every prx. It is scoped to the PS5 libraries (not FEX, Metal or the system frameworks), it covers their third-party objects, it does not depend on dyld interposing (which does not reach libSystem-internal calls in any case), and stdio is wrapped at fread/fwrite because their large transfers call read(2) inside libsystem_c. Not covered: libc++'s own I/O (no prx imports filebuf or fstream: 0 imports), raw `svc`, and native userspace code, which stays correct but slow and is left to the hot-path `HostRange` translation already in place.
(C) A real mapping at the guest address: impossible (above).
Choice: (B). (A) is rejected as a correctness mechanism. A declarative opt-in version of (A), with a parameter annotation the generator reads, used only on transient-buffer parameters of hot exports, stays possible later as a speed tool, not as the fix for EFAULT.
Prototype (this commit, off by default): `core/libs/hostsys/HostSyscallShim.cpp`, library `aps5_host_syscall_shim`, CMake option `APS5_HOST_SYSCALL_SHIM` (OFF), which links it into libc and every prx (`link_host_syscall_shim` in `core/libs/CMakeLists.txt`). It covers read, write, pread, pwrite, readv, writev, preadv, pwritev (iovec arrays copied only when a base needs translating), recv, recvfrom (address and length too), send, sendto, getentropy, fread, fwrite. The real functions come from libSystem by `dlsym`. A buffer across a window edge is passed unchanged and the kernel still returns EFAULT (no throw: callers include C code). Test `host_syscall_shim` at 0x400000000 and 0x4000000000: libSystem's own read returns EFAULT at the guest address, each shimmed call moves the alias's bytes, iovec arrays inside the window work, host buffers pass through, and the fault counter stays unchanged. Link check: libSceNet.prx relinked by hand with the archive (`.mac-work/scratch/va4/`) has its recv/recvfrom/send/sendto as hidden definitions and no longer imports them from libSystem. No prx defines any of these names (no duplicate symbols when ON). Not yet done: a build with the option ON and a title run.
Next: turn it ON after a SuperTuxKart title_run and the guest_displaced_* suites pass with it; extend it to the rest of the 54+19+13 list; add an import-inventory test that fails when a prx imports a libSystem symbol not classified as shimmed, identity or userspace, so a new library cannot silently reintroduce EFAULT. Once ON, the hand translations of kernel calls (sceKernelRead and the others) become redundant but harmless (the alias passes through), and the bulk-copy translations stay for speed.

## D37: Fixed guest mappings inside the dyld shared cache are relocated by a constant offset and returned through the in/out address (2026-10-14)
Context: ASTRO BOT (PPSA21564) makes its first memory call `sceKernelMapNamedDirectMemory(&addr = 0x300000000, 0x79800000, prot 0xf3, MAP_FIXED, align 2 MiB)`. On macOS 27 arm64 the dyld shared cache occupies [0x180000000, ~0x344364000) at this slide; its end is always above 0x339B14000 (D33's worst case without slide), so 0x300000000 is inside the cache on every boot. The cache is readable host memory nested by the kernel at exec. It cannot be moved or overwritten (D33, D35). It also cannot be displaced, because D31/D33 rely on a fault, and here a guest read would silently return cache bytes. Before this decision the request threw "straddles the edge of the displaced window".
Evidence on the title (static, unwrapped eboot; scripts in `.mac-work/scratch/va6/`, nothing from the game committed):
- `sceKernelMapNamedDirectMemory` (NID NcaWUxfMNIQ, PLT 0x74E71F0) has 2 direct call sites. 0x27cca3 is the first call: it stores `movabs 0x300000000` into a bss global `g_base`, passes `&g_base`, and right after the call reads `g_base` back. It hands that value to `sceLibcMspaceCreate`.
- `g_base` has exactly 5 rip-relative references in .text: 3 in this setup function, the teardown (`sceKernelMunmap([g_base], 0x79800000)`), and an "is pointer in arena" helper that computes `base <= p < base + size` from the globals. 0x379800000 (the end) never appears as an immediate.
- The other site is a generic wrapper (0x4a77f0). It returns the in/out value, and its fixed callers (0x400000000, 0x500000000) store the returned address (`mov [rbx+0x18], rax`) and use it from there.
- 19 `movabs 0x300000000` exist in all, but only one is the mapping hint. The page-aligned 0x3xxxxxxxx immediates (23 inspected) are packed dword pairs {0, 3} stored into struct fields, or a `bt` mask. About 10.9k 8-byte data values in 0x3xxxxxxxx are int pairs as well (28 look pointer-like, none in pointer tables). Verdict: ASTRO uses the returned address (about 90% confidence; byte-pattern scans cannot see a base built arithmetically).
Contract and prior art (research, primary sources):
- FreeBSD mmap(2) MAP_FIXED: "Do not permit the system to select a different address than the one specified" (https://man.freebsd.org/cgi/man.cgi?query=mmap&sektion=2). fpPS4 `rtl/mmap.pas` names SCE_KERNEL_MAP_FIXED 0x10 "map addr must be exactly as requested". So the console guarantees the address, and code may legally ignore `*addr`.
- EA's BSD-licensed EAStdC does ignore it: `source/EAGlobal.cpp` (L449, L492, L504-505) maps MAP_FIXED|MAP_NO_OVERWRITE at a constant shared by modules and uses the pre-call pointer.
- shadPS4 (`src/core/memory.cpp` L479/L559/L678), fpPS4, Kyty, sharpemu, prosper and upstream AnyPS5 never return a different address for a fixed request. On macOS, shadPS4 (x86_64 under Rosetta, `src/core/address_space.cpp` L39-43) simply excludes the commpage and GPU carveout from the guest layout, and fixed requests there fail. No project relocates a fixed request, and none solves this range: they run where the low guest layout is free (Linux, Windows, Rosetta) or fail.
Options:
(a) Relocate the request and return the real address. Correct for every title that reads `*addr` back, as ASTRO does. Wrong for code that keeps the constant (EAStdC-style). Such code then reads the shared cache silently, and its writes fault (the cache is read-only).
 - "FEX-side constant rebase" (rewrite 0x3xxxxxxxx immediates in translated code) is rejected on ASTRO's own evidence. Most such immediates are packed integer pairs, so a rebase would corrupt data. It also could not reach constants in data, computed bases or native code.
(b) A JIT window check on every guest access, redirecting [0x180000000, cache end) to an alias.
 - Cost, micro benchmark (`.mac-work/scratch/va6/bench/check.c`, M3, best of 9): an inline `sub, cmp, b.lo` before a load and before a store costs 1.79-1.90x of the plain load+add+store loop on a quiet machine (load 2.6: 0.29-0.31 → 0.54-0.55 ns per iteration, L1-resident and 32 MiB sequential; 1.9-2.3x at load ~5).
 - FEX has no scratch register guaranteed dead at memory ops (D33). A real implementation would also spill, like D33's patched-site stubs, whose cost on ordinary pointers was 5-8x in a tight loop. It would apply to every access of every title, DOOM included.
 - Not measured on DOOM: it would need a FEX IR change to every memory op (~35 IR ops, D31 c1), and (b) is rejected on correctness alone.
 - Native code (our prx libraries, libSystem, Metal) would still read guest memory at 0x3xxxxxxxx straight from the cache, silently. ASTRO's native code touches guest memory constantly: 103k native faults in 8 s on 0x4/0x5xxxxxxxx alone. The silent-corruption risk cannot be closed this way.
(c) Other: (1) Remove or move the cache: impossible (D35: SHARED_REGION_BASE_ARM64 is fixed; `_POSIX_SPAWN_RESLIDE` only moves the slide, and the minimum cache end 0x339B14000 is above 0x300000000 at every slide). (2) Run without the shared region: system dylibs exist only in the cache since macOS 11, so no. (3) Rosetta keeps the same layout, and it is out of scope (no Rosetta). No better option exists.
Choice: (a), deterministic.
- When a MAP_FIXED request (direct, flexible, or a virtual reservation) overlaps [0x180000000, min(DisplacedStart(), 0xFC0000000)) and lies inside the shared region, it is served at request + 0xD000000000. That target region [0xD180000000, 0xDFC0000000) is free arena between first fit (which grows up from 512 GiB) and the AMM ranges (top 64 GiB). The address is returned through `*addr`.
 - The offset is constant: every run gives the same addresses, and repeated or overlapping requests keep their relative layout. MAP_NO_OVERWRITE over an earlier relocation fails, and a replacing request lands at the same offset, as on the console.
 - If an unrelated mapping holds the target, the request becomes a hint there.
 - Each relocation prints `[libkernel] fixed mapping ... overlaps the host's dyld shared cache ...: relocated to ... (D37)`, so a title that later crashes on the constant shows why. `APS5_FIXED_RELOCATE=0` restores the refusal.
 - Fixed requests in the tail, the commpage guard or the carveout are unchanged (displaced, exact address). Requests reaching past 0xFC0000000 stay refused.
Risk: a title that ignores `*addr` after a fixed request in [0x180000000, cache end) reads dyld cache bytes silently, and writes fault. Only titles that ask for this range are affected. ASTRO, the one title known to, reads the address back. Recorded in TechnicalDebt.
Evidence: commits e09119816 (relocation, guest_displaced_memory cases) and a022e3426 (the displaced-stub unaligned path that the run past this point needed). ASTRO boot results are in PROGRESS (2026-10-14, VA6).

## D58: Displaced-access sites and stubs are freed with the code that holds them; register-offset stubs check the full address; native displaced writers are fixed at the source (2026-10-14)
Context: D31/D33/D49 patch every translated load/store that touches displaced memory to a stub, recorded in a 1M-entry site table with stubs in up to 512 one-MiB chunks. Nothing was ever freed: a 10-minute M3 soak or an M4 run could fill either (fatal for the next site). ASTRO BOT (PPSA21564) "patched" ~123k sites in 300 s (`.mac-work/logs/va8/PPSA21564-va8-va8-before.log`) and one core ran at 100% the whole time.
Measured (APS5_DISPLACED_STACKS=2048, run va8-before-sites): almost all of those "sites" were one instruction, `ldr s18, [x17, x4, sxtx]`, at stub addresses 0x48000 apart (2048 x 144 bytes): a register-offset access whose base x17 is small and whose index is the displaced pointer. The stub checked xN alone, took the plain path, faulted inside the stub and patched that copy to a new stub, so every execution added one stub and walked the whole chain (unbounded growth, quadratic time).
Options: (a) reclaim only; (b) also fix the register-offset check; (c) for frees: tombstones vs backward-shift deletion; hook FEX's block invalidation vs the code pool's Free.
Choice:
- Register-offset loads/stores (`[xN, xM, ext #s]`) compute `xN + ext(xM) << s` with one `add` (the load's option field is ADD-extended's) before each of the two range checks; the flip path (`eor xN`) is unchanged. The lower bound now compares 16 KiB pages with two `sub` immediates instead of `movz/movk/movk + sub` (one instruction shorter for the immediate forms, two longer for register forms; the window start is checked to be 16 KiB aligned at enable).
- Reclamation at `CodePool::Free` (every FEX code buffer is freed through it): FEX frees a buffer only once every thread has switched away from it (`CPUBackend::CheckCodeBufferUpdate`, `SignalHandlerCodeBuffers`), and a stub is entered only from its site and returns into that site's code, so no thread can be inside a freed site's stub. Block invalidation (SMC, unload) leaves code in the buffer, so its sites stay until the buffer goes; hooking it would need the same lifetime proof per block and gains nothing for the table bound. The listener runs before the pool lock (fault handlers take site lock -> pool lock).
- `GuestDisplacedCodeFreed(start, end)`: under the site spinlock with all signals blocked, scan the home slots of [start, end) and on to the first empty slot, delete by backward shift (no tombstones: lookups stay short under churn), put each stub slot on its chunk's free list (first word becomes BRK #0xd16, link in the writable view), then forget sites inside freed stubs (depth 4). Live sites are capped at 7/8 of the table (linear probing near full runs in signal handlers).
- Native libraries that read or write guest structures in place were audited statically (Explore sweep of NGS2, AJM, AvPlayer, AudioOut, Audio3d, Pad, UserService, VideoOut, libkernel equeue/time/event flag, Fiber, SaveData, AgcDriver, libSceAgc) and dynamically (APS5_DISPLACED_STACKS_NATIVE=1 on ASTRO), and fixed with host views (HostRange/HostPointer/Agc::Command::Host); guest-visible pointers and handles stay guest addresses.
Measurements: churn test (guest_displaced_memory SiteReclamation): two threads patch and free 200k sites through a 2048-site cap and 2 extra chunks, then 1.28M at the built-in caps (more than the table): no leak, live sites and slots back to the start, ~4 s. ASTRO BOT 300 s headless --validation (build-metal at a3805ebb9 vs build-va8): total displaced faults 122,880 by 256 s (still rising ~170/s) -> 4,096 by 35 s and fewer than 8,192 by 300 s; unpatched (native) faults 72 -> 0; title CPU 281 s -> 61 s over the run (the chain walker is gone); live sites ~4k, sites in stubs 0.
Evidence: commits on branch va8 (libc reclamation and stub check, fex CodePool listener, kernel/libs/ngs2/ajm/fiber/avplayer/savedata/agcdriver/agc host views); tests guest_displaced_memory (RegisterOffsetSites, SiteReclamation), fex_code_pool FreeListener, fex_displaced_churn, guest_displaced_status, guest_displaced_audio, guest_displaced_fiber_media, guest_avplayer, guest_displaced_shaders, agc_commands; logs `.mac-work/logs/va8/`.

## D62: Wave64 compute at one guest lane per invocation where the wave's other lanes do not matter, with threadgroup exchanges in one-wave threadgroups (2026-10-15, SHD9)
Context: TechnicalDebt `metal-first-frame-compile` lever (1). MSL lays wave64 compute out at two guest lanes per host invocation (laneCount 2: lanes l and l + 32 of a wave in one invocation of a 32-wide SIMD group), so ballots, votes and lane reads see the whole wave in one SIMD group, but every per-lane value and statement is emitted twice (`vN`, `vN_h`). Model (front end): EXEC and VCC are per-lane bools (GetExec), vector register writes are `Select(exec, new, old)`, memory accesses take the lane's active bit as their last argument, and every 64-bit mask the scalar code reads is a `Ballot` (s_and_saveexec, v_cmp to VCC/SGPR pairs, s_*_b64 on EXEC); wave-mask branches (s_cbranch_execz/vccz and their non-zero forms) carry a per-lane condition that the backend votes over the wave.
Analysis (MetalBackend/src/MslLaneLocal.cpp, MslPlanWave64LaneLocal, on the optimized IR; one lane L per invocation):
- (a) cross-lane reads: DPP (rows, DPP8), v_permlane16/x16, ds_swizzle, ds_bpermute/permute stay in L's 32-lane half, which at one lane per invocation is one host SIMD group (guest lane = thread index in the threadgroup & 63, the two-half layout's mapping): SIMD-group shuffles of `lane & 31`, allowed in whole waves (threads % 64 == 0). v_readlane/v_readfirstlane read any lane: only in one-wave threadgroups (64 threads), through threadgroup memory. ds_append/consume block.
- (b) ballots: L's own bit is exact for consumers that read only L's bit: masks may flow through and/or/xor/not, selects, phis (never mixing word 0 and word 1) and leave through the front end's own-bit extraction (Select(LaneId < 32, lo, hi) >> (LaneId & 31) & 1). Any other use (SCC = mask != 0, s_bcnt1, 64-bit masks, stores of a mask) needs the other bits: exact ballots through threadgroup memory in one-wave threadgroups, else the program keeps two lanes per invocation.
- (c) wave-mask branches decided by L's own condition. L leaves the wave's path only while inactive (zero forms: L's condition true, another lane's false; non-zero forms the other way round) and skips the region R the wave runs meanwhile (reachable from the wave's successor before the immediate post-dominator M, which must be L's successor). Exact when, evaluated for L under the deviation's fact (L's condition, propagated through not/and/or and backwards through own-bit extractions to the ballot predicates) with an optimistic fixpoint over R (a value is a constant, "its value when L deviated", or unknown; selects with a known condition pick their arm; phis join their incoming values from R; values R may read before redefining them, as loop-carried phis, start from their value at the deviation): (1) every effect in R is masked off for L (memory writes/atomics with a false active bit; nothing else), (2) every value leaving R (M's phis on R's edges, values defined before the deviation and read after M) equals what L carries on its own edge, and (3) R holds no convergence point (cross-lane reads, exact ballots, lane reads, s_barrier, LDS accesses ordered by wave LDS barriers). By induction over L's path, L's state after M is its state in the wave. A branch that fails votes through threadgroup memory in one-wave threadgroups (and then is itself a convergence point for the branches around it, to a fixpoint); elsewhere it keeps two lanes per invocation.
- (d) LDS: one-wave threadgroups keep MslWaveLdsScope's threadgroup barriers (lockstep order of the wave's LDS accesses); in larger workgroups every LDS access must be separated from every earlier LDS write (and every write from an earlier read) by an s_barrier on every path (dataflow over the CFG).
- Workgroups up to 256 invocations (MslLaneLocalMaxThreads: twice the host invocations of the two-half layout against pipelines' maxTotalThreadsPerThreadgroup), and the 512-byte exchange buffer must fit beside LDS kept in threadgroup memory.
Emission: laneCount 1 with `MslEmitterState::laneLocal`: own-bit ballots; per-lane conditions for proven branches; `threadgroup uint aps5_wx[128]` in two alternating halves (one barrier per exchange: a half is written again only after the next exchange's barrier) for votes (simd_any/simd_all per SIMD group, combined), exact ballots (simd_ballot per SIMD group) and lane reads (each lane's value at its guest lane). Switch: SpirvTarget::mslWave64LaneLocal (CacheKey, request serialization version 25), set by MetalDevice (APS5_MSL_WAVE64_LANE_LOCAL=0 off); agc_metal_msl_corpus replays with the device default.
Options considered: (i) only programs without any ballot/vote/cross-lane read (strict reading of the brief): 7% of ASTRO's wave64 compute bytes; (ii) + per-lane branch proofs and own-bit ballots: still blocked by LDS in divergent code (40%) and DPP/readlane (42%); (iii) (ii) + threadgroup exchanges in one-wave threadgroups and half-wave reads as SIMD-group shuffles (chosen). Not done: lane reads across waves of a multi-wave threadgroup (barriers would have to be reached by every wave; per-wave votes diverge), spin-waits between SIMD groups (no forward-progress guarantee).
Evidence: agc_metal_wave64_lane_local (GPU, new): 13 configurations of 5 programs (if/else and nested ifs over execz skips with stores in the arms, a per-lane-trip-count loop with execz exit and stores inside, an own-bit SGPR mask, a do-while with an execnz back edge, single-wave LDS exchange without s_barrier, two-wave LDS through s_barrier, s_bcnt1 of EXEC, vccz over all EXEC lanes, DPP row shifts + permlanex16 + ds_swizzle + ds_bpermute + v_readlane 31/63 + v_readfirstlane in a divergent if; 48/64/128/256 threads) translated with and without the flag over inputs that diverge within and across halves and whole waves taking one side: every output dword bit-identical, and the layout as expected (9 lane-local, 4 kept). agc_metal_wave64_lane_local_plan (CPU, new): the layout decision and no second-half names in lane-local MSL.

## D78: Points and lines carry only their own per-vertex corners; mesh points need no staging (2026-10-16)
Context: past D77, ASTRO BOT stopped at a mesh point list (11 parameters, 8 per-vertex locations): "Mesh unique scalar count of 148 exceeds limit of 124, Total mesh size (41280) exceeds the maximum mesh size allowed (32768)", and after the first fix at the staging budget (190 vertices: 37096 bytes with LDS). The triangle-vertices mode emitted three corner fields per per-vertex location for every primitive, though a point has one corner and a line two (D69/D75 repeat the last), and staged every vertex record in threadgroup memory.
Options: (a) device-memory staging for every mode (a per-draw arena binding for mesh functions, as compute's device LDS); (b) output only the primitive's own corners (all stages read the missing ones from the last), and for points put each vertex's own values on its record (flat from the only vertex), which removes the staging; split the subgroup's vertices over the grid by Metal's 32 KiB mesh output.
Choice: (b), MslAbi Version 20 (17 before the rebase onto sync4). `APS5_PRIMITIVE_VERTICES` now also reaches the fragment function, whose `aps5_pv_<L>(v, c)` reads corner min(v, N - 1). Mesh pipeline failures now name the mesh function's output locations and macros.
Evidence: agc_metal_msl_mesh links every triangle-vertices case with N = 1 and 2 (mesh and fragment macros), agc_metal_msl_per_vertex the vertex path's; agc_driver_mesh_per_vertex_inputs and agc_driver_pixel_barycentric_emulation (point and line cases) stay bit-identical to the vertex path. Gap: no unit test reaches more than one point run (the test programs' records are too small); lines and triangles with records past the staging or mesh-output budgets still fail their library compile with an `#error` (device-memory staging, option a, is the general fix).

## D81: Index expansions gather GPU-written indices on the GPU (W1, 2026-10-16)
Context: the PERF5 audit's top waste W1 is `Recorder.Sync` inside draws and dispatches on queue 0. In Showcase 1.0.2 (WASTE1 s0, build-waste1 at fc2fd9f9c, APS5_PROFILE_DRAW, `sample` of queue 0), 581 of the 1,231 samples in `Recorder::Sync` came from MetalDraw.mm's index expansion (`SettleRange` before the CPU reads the indices: fans, last-vertex provoking rotation, list restarts, the triangle-vertices table), each a full drain of the recorder because recorded GPU work (or a label) still writes the index range; `other@` 187 syncs / 9.4 s in [recorder].
Options: (a) skip the rotation when no fragment input is flat (changes vertex order, not general: fans still expand); (b) a GPU expansion kernel for every case (restart needs values to segment, a prefix scan); (c) plan the expansion over positions on the CPU (it depends on positions only unless a primitive restart matters) and gather the guest indices at those positions on the GPU.
Choice: (c). `IndexGather` (RecorderKernels.h, one thread per index) reads 16/32-bit guest indices through the wrapped import into a stream allocation, recorded before the pass (a compute encoder ends an open pass; the render encoder's queue barrier orders the index fetch after it). `FlushForGpuRead` records queued labels and storage stores over the range first; when it had to wait for a CPU write-back the CPU path runs. Restarts that matter, the triangle-vertices table, unwrappable or misaligned memory keep the CPU read. APS5_CPU_INDEX_EXPANSION=1 restores it. Counters: [cpuwaits] (APS5_PROFILE_DRAW).
Evidence: agc_metal_draw_index_gather (G3): 16- and 32-bit fans over indices a recorded fill writes over stale CPU bytes are gathered (counter) and draw the right half exactly; a restarted list over filled indices is read after one sync; CPU-written fan indices take neither path. Measurements: PERFORMANCE.md (W1).
- Rebased onto sync4 (branch land5, REBASE5, 2026-10-20; built, untested). Upstream solves nothing here: the index expansion's sync is not on the flush-hook or collect paths that 6643e2870c / 192d95c5d1 speed up. The IndexGather helper kernel sits after upstream's DispatchArguments in HelperKernel.

## D82: Storage image snapshots of GPU-written memory are copied on the GPU for direct uploads (W1, 2026-10-16)
Context: ASTRO BOT (WASTE1 a1, same build): queue 0's `Recorder.Sync` was 68.6 ms per 530 ms frame; of the 167 `sample` hits in `Recorder::Sync`, 141 (84%) were `StorageTexture::captureGuestBytes` (from `Refresh -> upload`, and `FillClear -> keepComparable`): the snapshot behind the untracked comparison (`original`) is read on the CPU after the flush hook drained the whole recorder, because recorded work (a dispatch's in-place writes, another image's write-back) writes the surface in the open batch. Showcase: 248 of 1,231.
Options: (a) wait only for the batch that writes the range (the writer is in the open batch: the same drain); (b) defer the capture to the next comparison (CPU writes since the upload would enter the snapshot); (c) a GPU copy of the units at the upload's place in the queue, landed in `original` at completion; (d) W2/D74 (watched imports make the memory tracked, so no snapshot is needed).
Choice: (c) for the direct upload only, besides (d). The upload's detile reads the image content from the host import at its place in the queue, so a copy recorded there holds exactly the bytes the image holds: the later comparison stays consistent with the content whatever the CPU writes around it. A per-unit ticket (`layerSnapshot`) keeps an older copy from landing over newer bytes (a CPU capture or `forgetSnapshot` clears it); readers of `original` (`settleSnapshot`: the Refresh equality check, `compareUntracked`, the baseline check, the CPU write-back) wait for a copy not yet landed. Captures whose content does not come from that read (GPU clears, fills, image copies: `keepComparable` and the clear path) keep the CPU read: their snapshot must predate CPU writes made after the call; a first version that copied those on the GPU, or that copied whenever any write was pending, lost CPU-written bytes in agc_driver_store_over_untracked ("a fill of the surface", "an image copy into the surface"), which is why (c) is limited to the direct upload. Shadowed units, a pending CPU write-back over the units and memory without a host import keep the CPU read too. APS5_CPU_TEXTURE_SNAPSHOT=1 restores it. Counters: [cpuwaits].
Evidence: agc_driver_storage_gpu_snapshot (G4): a buffer fill and an image store in one submission; the store's upload snapshot is copied on the GPU (counter), the 8 stored texels and the fill reach guest memory after the write-back, and a CPU page written while the results are pending is kept (the write-back's block keep rule). agc_driver_store_over_untracked passes. Measurements: PERFORMANCE.md (W1). Gaps: TechnicalDebt metal-w1-cpu-waits.
- Rebased onto sync4 (branch land5, REBASE5, 2026-10-20; built, untested). Checked against upstream:
  - 69702ef105 (in sync4's Texture.mm twin) added a stored-save path for GPU-side write-backs outside the write watch: a host-visible `savedBytes`, a per-unit `savedTicket`, `applyStoredSave` at the batch's completion, cancels wherever bytes are replaced, and `awaitStoredSave` for readers. That is D82's own landing machinery in general form, so D82's `layerSnapshot` tickets, `forgetSnapshot` and landing callback were dropped. The upload's GPU copy now writes `savedBytes` and commits a stored save. D82 still keeps the units' `layerOriginal` while the copy is in flight, and `settleSavedOver` (SyncThrough the units, then a full Sync) makes readers of `original` wait. The `[cpuwaits]` 'landed' count is gone.
  - 6643e2870c (the flush hook skips the registry mutex when no pending image overlaps) and 192d95c5d1 (collect walks skip 4 MiB runs that no write stamped): both make the no-pending case cheaper. D82 targets the case where recorded writes are pending over the surface, which still drained the recorder. Not redundant.
  - 537bbcc96c (the presenter adopts the newest collect epoch, so an untracked display image keeps its comparison memo): sync4 has the shared GuestMemory::AdoptLatestCollectEpoch, but the Metal present (MetalPresentation.mm PresentDisplayBuffer) does not call it. That path flushes for a GPU decode or reads the display buffer, and has no resident-image refresh like VulkanDevice's. Not mirrored here; it is a separate Metal follow-up, outside D81/D82 (since mirrored by FIX6, see the D72 round-4 follow-up).
