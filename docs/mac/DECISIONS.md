# Decisions

One entry per decision. Newest at the bottom. Format: context, options, evidence, choice, date.

## D1: Fork, not upstream (2026-10-12)
Upstream accepts macOS only as x86-64 + MoltenVK with unchanged rendering (issue #1). Our goals (arm64, Metal, reworked rendering) conflict, so we work on branch `mac-native` and push nothing without the user's approval.

## D2: No Rosetta in the product path (2026-10-12, user decision)
The game process is arm64 only. Reasons: the user wants native performance; Apple ends Rosetta support after macOS 27. Rosetta as a *test-only* oracle for the CPU translator is still an open question for the user (MISSION §6.4).

## D3: Metal, not MoltenVK (2026-10-12, user decision)
Rewrite the GPU path: new `MetalBackend` in the shader recompiler and a Metal driver in libSceAgcDriver, designed for TBDR. Keep the recompiler front end (decoder, control flow, translation, IR, optimization) because it encodes measured RDNA2 behaviour. MoltenVK failure list in MISSION §5 is the requirements list.

## D4: Generic binary translation, no per-game reverse engineering (2026-10-12, user decision)
The CPU layer is a game-agnostic x86-64 → ARM64 translator: AOT from executable metadata (`.eh_frame`, relocations, NID tables) plus a JIT fallback with a persistent cache. Open sub-decision for M1: LLVM AOT backend vs a direct emitter, and whether to borrow from FEX (MIT ≤ `ac555dd8`). Decide with measurements.

## D5: Storage budget 100 GB (2026-10-12, user decision)
Everything the port creates stays ≤ 100 GB; `tools/mac/disk_budget.sh` enforces it. Only storage exceptions require asking the user.

## D6: FEXCore is the M1 translator engine; our own AOT discovery and per-title cache on top (2026-10-12)
Context: D4 left open LLVM AOT vs a direct emitter vs borrowing FEX. arvindfroi's runner `aps5-fex` (mugurc/AnyPS5#4, merged here) already runs guest programs through FEXCore in-process.
Options and evidence (`.mac-work/research/translator-perf.md`, `runner-arch.md`):
- (a) FEXCore JIT + our AOT discovery (`.eh_frame`, relocations, exports, init arrays) + persistent cache: est. 0.7–0.9× native on integer loops, 0.6–0.9× SSE, 0.4–0.7× AVX2 (no SVE on M3: upper YMM halves live in memory); 2–4 agent-days.
- (b) LLVM lifter + JIT fallback: published lifters run 1.5–4.8× slower than native (Lasagne, Instrew, Elevator); yabanana's #1553 covers 3 scalar functions and relies on per-game annotations (forbidden by MISSION §1). 3–6+ agent-weeks, and still needs a JIT.
- (c) Own emitter: months to reach FEX's coverage (AVX2, x87 80-bit via SoftFloat, TSO modes).
- Measured on this M3 (cycles/op, `.mac-work/research/tsobench/`): LDAPR/LDAPUR 0.60 vs LDR 0.35; STLR 1.0 vs STR 0.5; ordered vector accesses 11–21×. Taken under heavy load: ratios valid, absolute ns not.
Licence: arvindfroi/FEX `cad0c096` audited (`.mac-work/research/fex-licence.md`): FEX-2607 + 55 willfaust commits ending at `ac555dd8` (MIT) + 15 FEX-Emu backports (MIT, byte-identical to upstream) + 6 arvind commits; no willfaust commit after `ac555dd8` (his GPL-3 switch is `188e8224`, 2026-08-28). Nested deps: fmt (MIT), xxHash lib (BSD-2), range-v3 (BSL-1.0), unordered_dense (MIT), cephes (BSD), SoftFloat-3e (BSD-3). All GPL-2.0-compatible.
Choice: (a). Pin `3rdparty/FEX` at `cad0c096` (no `branch =` drift), guard it with a licence test, keep a git bundle backup in `.mac-work/ref/`, take future FEX fixes only from FEX-Emu (MIT), never from willfaust after `ac555dd8`. Keep FEX patches local (FEX-Emu's CONTRIBUTING forbids AI-generated contributions, and we push nothing without the user). Revisit only if M1 microbenchmarks stay below 0.7× native on integer/SIMD loops after tuning; LLVM stays an option for measured hot functions in M4.

## D7: CPU translator test oracle: FEX's x86 ASM unit tests, no Rosetta (2026-10-12)
Context: MISSION §6.4 (no x86 hardware here). FEX ships ~2,222 nasm unit tests whose expected register/memory values are checked on real x86 hardware in FEX's CI (MIT). Choice: port them to run under `aps5-fex` as the per-instruction oracle, plus SDM-derived expectations for anything they miss. Rosetta is not needed as an oracle, so the user question in §6.4 is moot. 1,020 tests use scratch addresses below 4 GiB, which macOS arm64 can't map: the harness moves 1,007 of them up by `0x10_0000_0000`; 13 can't be moved (recorded skips). All 2,222 assemble with nasm 3.02.

## D8: M2 shape: MetalBackend from IR + the VulkanDevice API implemented on Metal (2026-10-12)
Evidence (`.mac-work/research/m2-scope.md`): the IR (SSA, 469 opcodes, structured if/loop markers) has almost no SPIR-V dependency; SpirvBackend has one call site (`Recompiler.cpp:427-436`). The driver has no abstraction layer, but only 23 files (~27.4k lines) call Vulkan, and ~329 of the 336 `agc_driver_*` tests use only the public `VulkanDevice` API. Upstream notes the suite already passes under MoltenVK on Apple GPUs except 16 hardware-limit tests.
Choice: `MetalBackend` emits MSL at the SpirvBackend call site (SpirvBackend keeps compiling for differential tests). The `VulkanDevice` API is implemented on Metal in Objective-C++ under `libSceAgcDriver/specifics/macos`, swapped in by CMake on Apple with an overlay include directory, so upstream files stay untouched except CMake. Vulkan-Headers stays as header-only enum/struct types; nothing loads or calls Vulkan. SPIRV-Cross (core files dual "Apache-2.0 OR MIT", used under MIT) may be used in dev builds only, as a bridge and differential oracle, never shipped. Rejected: a Vulkan-on-Metal layer (violates D3), a new abstraction layer (rewrites a Vulkan path we can't test here), a clean-slate driver (loses behaviour the tests check). Metal 3 vs Metal 4 command API: decided in `docs/mac/M2_DESIGN.md`.

## D9: Two parallel build streams; milestones still close in order (2026-10-12)
Context: CLAUDE.md allows at most two live build directories; the M3 Air has 8 cores. The CPU stream (M0 → M1 → M3 integration) and the GPU stream (M2) share almost no files. Choice: main worktree + `build-arm64` for M0/M1; a git worktree `.mac-work/wt/metal` (branch `mac-native-metal`) + `build-metal` for M2; agents sharing a build directory serialise ninja/ctest with `tools/mac/buildlock.py`. Prep work that needs no build (tools, design, title preparation) runs in build-less worktrees. Each milestone is still closed in order with its exit criteria verified.

## D10: No hardware TSO; emulate x86 ordering with LRCPC (2026-10-12)
Evidence: the TSO enable bit is set only by the kernel (Rosetta); no API, entitlement or sysctl in the macOS 27 SDK exposes it, and the TSOEnabler kext needs SIP off. Hypervisor.framework lets a VM vCPU enable TSO (probed here with an ad-hoc-signed binary: worked; one VM exit ≥3 µs), which is too slow for a game process calling native libraries constantly. Choice: FEX's default ordering (integer loads/stores LDAPR/STLR, vector ordering off, stack accesses unordered); further elision (frame-pointer locals, TLS, read-only data) only with measurements in M4.

## D13: Vendor FEX at FEX-Emu FEX-2610 plus our macOS series (supersedes D6's pin) (2026-10-12)
Context: M1 needs JIT results persisted and reused. Evidence (`docs/mac/M1_DESIGN.md` "Code cache: verdict", file:line checked): the pinned FEX's FXCC cache is off by default (`EnableCodeCachingWIP=false`), has never worked on macOS (`CodeCache.cpp:607-612`), is invalidated by every FEX rebuild, never checks guest bytes, and needs a Linux-side generator; the `.eh_frame` AOT generator is never called. FEX-2610's DiskCache lives entirely in FEXCore, caches ordinary JIT output, checks guest bytes on every hit, is address-independent, capped at 1 GiB and uses `flock`. A trial rebase of the macOS delta (61 commits after dropping the 15 backports already upstream) stopped 14 times with 45 hunks (30 in code we build; the code-buffer cluster onto upstream's `SharedCodeBufferManager` is the hard part). Staying on the pin would mean 400–700 runner lines on the broken FXCC path; the rebase is ~3 agent-days but also brings ~3 months of upstream fixes.
Options for hosting the rebased FEX: (1) a fork on GitHub (needs a push, i.e. the user's approval); (2) FEX-Emu as the submodule plus patch files applied at configure time (pristine upstream, but every FEX edit during active development must be re-exported); (3) vendor it in our repo.
Choice: (3). `git subtree add --squash` FEX-Emu `FEX-2610` at `3rdparty/FEX`, then apply the slim macOS series (willfaust ≤ `ac555dd8` + arvind's, dropping Windows/iOS-only commits) with `git am --directory=3rdparty/FEX`, preserving authorship; FEX's own `External/` dependencies become submodules of our repo. Updates come with `git subtree pull --squash` from FEX-Emu only. The licence guard (`tools/mac/check_fex_licence.py`) checks the recorded upstream base and scans for GPL-3 markers. No push is needed, so the user question in M1_DESIGN R is moot. Keep the git bundle of `cad0c096` until M1 closes.

## D15: Build and test conventions for the arm64 fork (2026-10-12)
- The full macOS build defaults to arm64 (top-level CMakeLists.txt); x86_64 stays selectable with `-DCMAKE_OSX_ARCHITECTURES=x86_64`. Reason: this fork's product is arm64-only (D2).
- GPU tests carry an explicit per-test `gpu` label (468 tests in libSceAgcDriver, libSceAgc, libSceVideoOut): `ctest -LE gpu` is the non-GPU suite; `-L gpu` is run one at a time with timeouts only (GPU safety). A directory `LABELS` property is not enough: CTest ignored it for tests that set `WORKING_DIRECTORY`.
- `no_x86_build_path` (the M0 "no x86 on the arm64 path" proof, ~12 min on all cores) carries the `slow` label: routine runs use `-LE "gpu|slow"`, milestone ends run it.
- Guest-state operations (getcontext/setcontext/makecontext/swapcontext, sigsetjmp/siglongjmp, the sceKernelRaiseException register snapshot) on arm64 go through runner hooks; without a runner they validate arguments and throw a `std::runtime_error` naming the function, and their tests skip with that reason (M1 package G wires them).
- Agents sharing one worktree commit only named paths (`git commit -- <paths>`), because the index is shared.

## D16: M2 architecture (Metal 4 driver, MslAbi, twins, caching) (2026-10-12)
Full text with evidence: `docs/mac/M2_DESIGN.md` §1 (on `mac-native-metal`). Summary:
- **Metal 4 command model** for every queue the driver records on; one `MTL4CommandQueue` + one `MTL4Compiler` per device (a process holding >100 Metal 4 queues panicked an M3 Max on 27.0.1). Probe on this M3: both APIs ~1.0–1.3 µs CPU per dispatch; Metal 4 without barriers overlaps 1000 dispatches (2 ms vs 5–8 ms); it maps 1:1 onto upstream's Vulkan-shaped recorder (stage-mask barriers, allocators, untracked resources, address bindings, shared events); Mesa KosmicKrisp is Vulkan 1.4 conformant on the M3 using Metal 4 only. Gap: no tessellation in `MTL4RenderCommandEncoder` → skip first, then a Metal 3 side queue with event hand-off, mesh-shader tessellation in M4. Presentation via Metal 4 with a Metal 3 fallback switch. Bring-up barriers are conservative; M4 relaxes them from guest acquire/flush packets.
- **MslAbi v1**: four fixed buffer slots per function (dense per-stage descriptor table as a Tier-2 argument buffer written by the CPU, 256 B push data, large-LDS arena, driver-data record); specialization constants → function constants; each shader reports its layout (`MslAbi::Reflection`) and the driver binds by it. Changes are append-only with a version bump.
- **Twins**: the class keeps the name `VulkanDevice` (5 `make_shared<VulkanDevice>` call sites); Metal versions of upstream driver files live under `specifics/macos` with overlay headers searched first and per-package swap lists; transitional Vulkan handle types may carry Metal objects until every user is twinned. M2-end check: no Vulkan-calling original left in the Apple build (`nm -u … | grep ' _vk'` empty).
- **Guest memory** wrapped in place per allocation (`newBufferWithBytesNoCopy`, shared, untracked, one residency set), never the whole arena, never PROT_NONE/executable pages (mirrored by copy with write-back instead).
- **Shaders**: MSL text from the IR with prelude chunks owned by instruction families; `ulong` native, f64 in software, every IR value function-scope, every loop bounded by a runtime guard that records a `LoopLimit` fault (also protects the GPU from runaway guest loops). Compile with `MTL4Compiler` on background threads at shader registration; pipelines persist in a per-title `MTL4Archive` (binaries-only serializer; binaries+descriptors fails on 27.0.1), `MTLBinaryArchive` fallback; "second run compiles 0 pipelines" = archive lookups that cannot compile.
- **No SPIRV-Cross on the critical path** (MetalBackend already runs real tests; hardware-measured expected values are the oracle).
- **Skips** only for documented Apple hardware limits, via `tools/mac/m2_skip_allowlist.txt` + `check_skips.py --job macos`; f64 and 64-bit atomics are emulated, not skipped.
Foundation result: `agc_driver_vop1_control` passes end to end on the GPU via MetalBackend; G1 baseline 29/196 compute tests pass, 29 skip, 138 fail, 0 hangs.

## D18: Runner defaults: strict split locks, opt-in disk cache (2026-10-12)
- FEX's `StrictInProcessSplitLocks` is on by default: unaligned locked accesses that cross 16 bytes are otherwise emulated with two CASes and tear (measured: 11 of 12 wrong counts across 4 concurrent copies without it, 12/12 correct with it).
- The JIT disk cache (FEX-2610 DiskCache, content-checked) is enabled when `APS5_FEX_CACHE_DIR` is set or a directory above the executable is named after a title ID; `aps5-fex --precompile` seeds it ahead of time from `.eh_frame` FDEs, exports, relocation targets, init/fini arrays and the entry point.

## D19: GPU safety rules after the 2026-10-12 kernel panic (user-approved 2026-10-12)
Evidence: `.mac-work/feedback/gpu-safety-proposal.md` (panic during process teardown of a test using an untested, half-edited Metal 4 device; one residency set never removed from the queue). The user lifted the GPU freeze ("all gpu tests are allowed now") on these terms:
1. GPU tests run only through `tools/mac/gpu_suite.py` (or a ctest call wrapped by it), which refuses when the build that produced the binaries has uncommitted changes under `core/`, when any GPU test binary or the prx is stale vs its inputs, when the 1-minute load average is > 6, or when a compiler/linker is running. Record prx hash + HEAD per run.
2. Canaries first in every session (3 known-good tests); stop on any failure.
3. A shader corpus that doesn't compile (offline `xcrun metal` once installed, else `agc_metal_msl_compile`) means its tests are not launched.
4. Validation (`MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1`) for new shader families, device/recorder/residency/teardown changes and quarantined-test reruns.
5. Driver teardown hygiene: every residency set removed from the queue, wait for the last submitted value before releasing, drop `__DATA` wrappers, join the release thread.
6. One test per process, timeout ≤30 s, 2 s pause between tests. Quarantine list fails closed.

## D20: Per-vertex fragment values are emulated through triangle-vertices draws (2026-10-13)
Context: user order (2026-10-13 ~05:50) "no Apple limits, only things still to emulate". RDNA pixel shaders read per-vertex attribute values (`v_interp_mov` P0/P10/P20, `v_interp_p1ll/p1lv/p2_f16`, exact I/J); Vulkan has them through VK_KHR_fragment_shader_barycentric, upstream emulates them with a generated geometry shader otherwise. Metal's per-vertex fragment values (`vertex_value<T>`) are Apple10-only (Metal Feature Set Tables, 2026-05-21, https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf), and Metal has no geometry stage. `[[barycentric_coord]]` is Apple7+ but documents no relation to a vertex order the shader could index.
Options: (a) mirror upstream's geometry-shader emulation in the vertex function: a non-indexed draw with 3 host vertices per guest triangle, each running the guest vertex program for its triangle's 3 guest vertices and emitting the corner values as flat outputs plus one-hot corner weights as interpolated barycentrics; (b) a compute pre-pass writing the vertex outputs to a buffer, the fragment function reading them by `[[primitive_id]]` (needs a second pass, an output buffer sized per draw, and primitive_id ordering that matches the index expansion); (c) mesh shaders (object/mesh functions emitting the triangle with per-primitive data).
Choice: (a). It reuses the rect-list expansion already in the emitter, shares its driver plumbing with DRAW's conservative-rasterization emulation (one contract, MslAbi Version 5: `BufferIndex::TriangleVertices`, `TriangleVerticesHeader`, macros `APS5_TRIANGLE_VERTICES`, `APS5_PER_VERTEX_LOCATIONS(_HI)`, `APS5_BARYCENTRICS`, `APS5_CONSERVATIVE`), and its corner order is the one the driver writes, so P0/P1/P2 and the weights agree by construction (no reliance on `[[barycentric_coord]]` ordering). The Metal target advertises `fragmentShaderBarycentricEnabled`; on the MSL backend the recompiler still translates with host interpolation first and re-translates with barycentrics only the programs that need them (16-bit interpolation now marks the program instead of throwing), so ordinary draws keep indexed drawing. Costs (3x vertex invocations, 3x varyings per per-vertex location, centre-only I/J) are in TechnicalDebt `metal-per-vertex-values`; M4 may use native `[[barycentric_coord]]` for I/J-only programs once its order is measured.

## D21: Conservative rasterization is emulated in the triangle-vertices mode (2026-10-13)
Context: user order (2026-10-13 ~05:50) "no Apple limits, only things still to emulate". The Metal API has no conservative rasterization (no property in the macOS 27.0 SDK headers, MTLRenderPipelineDescriptor included), and the Metal Feature Set Tables (https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) list none for Apple9 or Apple10; the allowlisted skip (`has no VK_EXT_conservative_rasterization`) was temporary.
Options: (a) GPU Gems 2 ch. 42 (https://developer.nvidia.com/gpugems/gpugems2/part-v-image-oriented-computing/chapter-42-conservative-rasterization) in the vertex function, which needs the whole triangle per host vertex: the D20 triangle-vertices mode already provides it; (b) a compute pre-pass writing grown triangles to a buffer, then a normal draw (an extra pass and a per-draw buffer); (c) mesh functions emitting the grown triangle (needs the MSL mesh stage, not ready).
Choice: (a), sharing D20's contract (MslAbi v5, `APS5_CONSERVATIVE` = 1 overestimate / 2 underestimate): DRAW 9ec6a7ffb (driver), 07fe3aac8 and a8aa31286 (MslConservative.hpp text hooks), SHD3 3f14bf8ad/639a3d393 (emitter calls the hooks). Vertex: each corner moves to the intersection of its two edges' offset lines (half-pixel projection on the edge normals, bounded for sharp corners). Fragment: exact separating-axis test (x, y, three edge normals) of the pixel square against the triangle, discarding misses; degenerate triangles become their vertices' box grown by half a pixel. `VulkanDevice::ConservativeRasterization()` is true on Metal.
Evidence: `agc_driver_conservative_rasterization` (off, overestimate incl. a sub-pixel and a degenerate triangle, off again) passes under --validation (gpu-suite/shd4-conservative, HEAD d80f1643a); its m2_skip_allowlist entry is removed. Costs and gaps: TechnicalDebt `metal-conservative-rasterization` (3x vertex work, triangles only, fixed half-pixel overestimation size). M4 may move both D20 and D21 to mesh functions to restore post-transform reuse.

## D22: Multisampled storage images are emulated as 2D arrays of layers * samples slices (2026-10-13)
Context: user order (2026-10-13 ~05:50) "no Apple limits, only things still to emulate". Four G4 tests (`agc_driver_prepared_shaders`, `_debug`, `_indirect`, `_uncached`) failed in MSL emission with "stores to a multisampled image, which Metal shaders cannot write" (gpu-suite/shd3-v2-upstream). MSL multisampled textures (`texture2d_ms`, `texture2d_ms_array`) support only `access::read` (Metal Shading Language Specification, section 2.9 Textures: https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf), and no Metal GPU family offers shader writes or atomics on them (Metal Feature Set Tables: https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf). Upstream fact (GuestTextureResource.cpp `resolveDimension`): guest T# types 14/15 (MSAA) are rejected on every platform, so today only placeholders reach these heaps at run time.
Options: (a) storage heaps of the MSAA dimensions become `texture2d_array` with slice = layer * samples + sample, the sample count a function constant; (b) a buffer backing with computed addresses (loses texture formats and texture atomics); (c) alias a 2D-array view or heap alias over the multisampled texture: rejected, a 2DMultisample texture can only be viewed as a multisampled type (newTextureViewWithPixelFormat:textureType: compatibility; Dawn forbids the same view for this reason: https://dawn.googlesource.com/dawn/+/10ec4ee7efb3c0fd10bdb7191da77cdd6d063ea9), and Apple documents no sample layout for heap aliasing.
Choice: (a), MslAbi v6 (MSIMG). Emitter: stores, 32-bit atomics and 64-bit lock-table atomics address slice l * n + s, bounds x/y, s < n and l < slices / n; n = `PipelineSpecialization::SampleCountBase` (12288) + resource for direct images (the binding plan supplies 1 << T# LAST_LEVEL), the T# metadata for table images. The MSL target needs `CapabilityStorageImageMultisample` as SPIR-V does. Binding plan: `Image2DArray` shape on MSL. Placeholders: single-sample 2D arrays. The run-time coherence design for real guest MSAA images (shadow 2D array, compute copy MS to shadow, per-sample render pass shadow to MS, dirty tracking) is recorded in TechnicalDebt `metal-ms-storage` until guest MSAA T#s are decoded.
Evidence: `agc_metal_msl_ms_storage` (new): MSL shape of 6 programs on the CPU, Metal compile, and dispatches of the store and 32-bit atomic programs on 8x8 backings of 2 layers * 4 samples writing exactly the addressed sample's slice (gpu-suite/msimg-t7, --validation). G4 results in PROGRESS.

## D31: Guest mappings in the macOS GPU carveout are displaced to an alias at guest | 1<<40 (2026-10-13)

(b) `com.apple.developer.kernel.extended-virtual-addressing`: on macOS `vm_map_set_jumbo` is a no-op (`#if defined(__arm64__) && !XNU_TARGET_OS_OSX`), so it neither moves nor removes the carveout; besides, an ad-hoc-signed binary claiming it is killed by AMFI at exec (exit 137, measured). (c) a guest→host remap: c1, rebase every guest memory access in the FEX IR (a sub/compare/select/add per access, every title, ~35 IR memory ops to cover, native libraries still unhandled); c2, fault-driven: back the window at an alias and redirect only accesses that actually touch it.
Measurements (c2 prototype and implementation, M3): one redirected access through the signal path ~2 µs; a translated store+load loop over 32 MiB at 0x4000000000 after its sites were backpatched: 0.99× the time of the same loop on an ordinary view of the same pages (memory-bound; the stub adds ~12 flag-free instructions); native `memset` of 1 MiB through the guest address ~4,600× slower than through the alias (two signals per store, no patching of signed code).
Choice: c2. Guest addresses in [64 GiB, 448 GiB) are backed at guest | 1<<40 ([0x110_0000_0000, 0x170_0000_0000), reserved PROT_NONE at arena init; one EOR immediate flips it). The arena tracks fixed mappings in the window apart from first-fit placement, which never lands there (zero cost for titles that don't ask). DirectMemory, arena commit/reset/protect, write watch, the AGC driver's GuestMemory primitives and its Metal no-copy import translate with `GuestArena::HostAddress` (Metal wraps the alias; offsets unchanged). A SIGSEGV/SIGBUS handler in libc builds, per faulting load/store, a stub that runs the instruction with its base register flipped (scratch registers outside every register field, sp moved past the 128-byte red zone, writeback propagated, no NZCV use) and resumes; JIT sites are then backpatched to `b stub` through the code pool's writable view with a range check on the base; native code returns from a far stub through BRK and SIGTRAP. aps5-fex's unaligned-access handler skips the window (macOS reports guard faults as SIGBUS/BUS_ADRALN). Covers the whole carveout, not only 0x4000000000. Limits in TechnicalDebt (native bulk access, exclusive pairs in native code, unaligned atomics, RLIMIT_DATA).

## D32: Raw console syscalls go through a FEX thunk at the console libkernel's syscall gadget (2026-10-13)
Context: oops-sdk homebrew (SuperTuxKart) makes raw FreeBSD system calls with `callq *0x8000004ea`, the address of the `syscall` instruction in getpid in the console's libkernel (oops-sdk `src/system/syscall.c`). On macOS 0x8000004ea lies in the dyld shared region (6-63 GiB), which cannot be mapped or displaced (it is real host code, not a guard), and the guest never executes a host `syscall`.
Options: (a) map a page at 0x8000004ea: impossible on macOS; (b) rewrite the call sites in the relinker: per-binary patching of indirect calls, fragile; (c) a FEX thunk: FEX lets the runner register a custom IR entrypoint at a guest address, so execution reaching 0x8000004ea branches to runner-provided code without that address being mapped.
Choice: (c), commit 6d087bca5 (FEX e7185c008 keeps custom IR entrypoints out of the disk cache). The runner registers a thunk trampoline from 0x8000004ea to an x86 gadget that saves the argument registers, xmm0 and xmm1, calls libkernel's `Aps5ConsoleSyscall_nid_no_patch` with {rax, rdi, rsi, rdx, r10, r8, r9} and returns as the console gadget does: carry set and a positive errno on failure. The handler maps the 19 numbers SuperTuxKart uses (read, write, open, close, unlink, chmod, getpid, ioctl, munmap, socket, connect, rename, mkdir, rmdir, clock_gettime, getdents, mmap, lseek and klog 601) onto libkernel's exports, and throws on any other number (CONVENTIONS: unsupported states throw).
Tests: guest_console_syscall (handler), fex fixture `console-syscall` (gadget ABI, carry flag, preserved registers).
